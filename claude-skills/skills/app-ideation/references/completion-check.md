# 완료 조건 검증 (기록·커밋 전 필수)

배경: 일부 실행이 2~5분 만에 끝나면서 강제 단계를 줄였다 (후보 12개, 본 존재 확인 1개 후 종료, 개선 라운드 생략).
빨리 끝나는 것은 목표가 아니다. **아래 조건을 모두 채우기 전에는 커밋·푸시하지 않고, 통과·유망 등록·승급 판정도 내리지 않는다.** (작업 중간 기록을 파일에 써 두는 것은 허용되며 권장된다. 실행이 끊겨도 진행분이 남도록 하기 위함이다.)

## 방법

1. 이번 실행에서 실제로 한 일을 **세어서** 아래 표를 채운다. 기억이 아니라 작업 메모·문서의 실제 개수로 센다.
2. `미충족`이 하나라도 있으면 커밋하지 말고 해당 단계로 **돌아가서** 채운 뒤 다시 센다.
3. 외부 원인(웹 검색 장애, 사용량 한도 등)으로 도저히 채울 수 없으면, 사유를 적고 실행 로그 결과 칸에 `불완전 실행`이라고 표시한다. 이때도 통과·승급 판정은 내리지 않는다.
4. 최종 표를 결과 문서(기획서 또는 no-pass 문서) 맨 아래 `## 완료 조건 검증` 섹션에 그대로 남긴다.

## NEW 모드

| # | 조건 | 목표 |
|---|---|---|
| N-1 | D2 현장 조사 검색 횟수 | ≥ 5 |
| N-2 | 출처가 붙은 페인 포인트 | ≥ 10 |
| N-3 | D3 후보 수 (각각 핵심 통찰 포함) | ≥ 15 |
| N-4 | D4 뻔함 제거 후 남은 후보 | ≥ 8 (모자라면 D2·D3 추가) |
| N-5 | D5 사전 검색: 남은 후보마다 2회 | 남은 후보 수 × 2 |
| N-6 | 본 존재 확인을 한 후보 수 | ≥ 3. 통과(NOVEL/DIFFERENTIATED)가 0개면 6개가 될 때까지 계속. 사전 검색 통과 후보가 바닥나면 D3로 돌아가 후보를 5개 이상 추가 생성해 이어간다(1회) |
| N-7 | 본 존재 확인 후보별 검색 쿼리 | 각 ≥ 6 (영어 2, 한국어 2, 앱스토어 site: 1, 대체 표현 1) |
| N-8 | 심사위원 실행: 존재 확인 통과 후보마다 6명 병렬 | 통과 후보 수(최대 2) × 6 |
| N-9 | 개선 라운드: 미달이지만 KILL 0(또는 해소 가능한 KILL)인 후보마다 새 심사위원 6명 | 해당 후보 수 × 6 (생략 금지) |
| N-10 | 통과·유망·탈락 판정에 적용한 규칙 문장 인용 | 후보마다 1줄 |

존재 확인 통과 후보가 끝내 0개면 N-8·N-9는 "해당 없음"으로 표시한다 (단 N-6을 채운 경우에만).

## PENDING 모드 (심사 대기 후보 재개)

| # | 조건 | 목표 |
|---|---|---|
| P-1 | 후보마다 심사위원 6명 병렬 | 후보 수 × 6 |
| P-2 | 개선 라운드 (미달·KILL 0) | 해당 후보 수 × 6 |
| P-3 | 존재 확인 14일 초과 시 재확인 | 해당 시 ≥ 6 쿼리 |
| P-4 | 처리 후 심사 대기 목록·블록 정리 | 완료 |

## 사용량 한도 등으로 중단될 때
심사 전에 중단되면 존재 확인을 통과한 후보 블록을 `OUT/pending/`에 저장하고 index.md "심사 대기 후보"에 올린 뒤, `불완전 실행`으로 기록·커밋한다 (이 경우에 한해 미충족 상태 커밋 허용, 판정은 내리지 않음).

## UPGRADE 모드

| # | 조건 | 목표 |
|---|---|---|
| U-1 | 직전 핵심 비판 Top 3와 비판별 대응 | 3개 모두 기록 |
| U-2 | 다음 단계 산출물 작성 | pipeline.md 단계 표의 항목을 모두 포함 |
| U-3 | 존재 재확인 쿼리 | ≥ 6, 그중 새 쿼리 ≥ 3 |
| U-4 | 재심사: 새 심사위원 6명 병렬, 각자 RESOLVED 항목 포함 | 6 |
| U-5 | 상태 전이: pipeline.md 규칙 표의 해당 행 인용 | 1줄 |
| U-6 | DROPPED면 같은 실행에서 NEW 수행 후 NEW 표도 채움 | 해당 시 |
