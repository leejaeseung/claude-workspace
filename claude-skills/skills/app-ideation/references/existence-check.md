# 존재 확인 절차 (필수)

목표: "이 아이디어가 이미 있다"는 증거를 **적극적으로 찾는 것**. 없다고 결론 내리려면 충분히 찾아봤다는 기록이 있어야 한다.

## 1. 검색 쿼리 만들기
후보마다 최소 6개 쿼리를 만든다. 반드시 아래 유형을 모두 포함:
- 핵심 기능을 설명하는 영어 쿼리 2개 (예: "app that reminds you to return borrowed items")
- 한국어 쿼리 2개 (예: "빌려준 물건 기록 앱")
- 앱스토어 지정 쿼리 1개 이상: `site:play.google.com` 또는 `site:apps.apple.com` + 핵심 키워드
- 대체 표현 쿼리 1개 (사용자가 문제를 부르는 다른 말, 경쟁 카테고리 이름)

추가로 가능하면: Product Hunt(`site:producthunt.com`), GitHub(오픈소스 구현), Reddit("is there an app that ..."), 크라우드펀딩.

## 2. 검색 실행
- 웹 검색 도구로 실제로 실행한다. 쿼리 수가 6개 미만이면 이 단계는 실패로 간주한다.
- 유망한 결과는 페이지를 열어 실제 기능을 확인한다 (제목만 보고 판단 금지).
- 대형 앱의 **한 기능**으로 이미 제공되는지도 확인한다 (예: 카카오톡, 네이버, 토스, 구글 지도, iOS/Android 기본 기능, 단축어/루틴).

## 3. 기록 형식 (기획서에 그대로 첨부)

```
### 존재 확인: <후보 이름>
검색 쿼리:
1. "<쿼리>" — 주요 결과 요약
2. ...
발견된 유사 서비스:
| 이름 | 플랫폼/링크 | 겹치는 점 | 다른 점 | 상태(활성/방치/리뷰 수) |
|---|---|---|---|---|
OS·대형 앱 기본 기능으로 해결 가능한가: 예/아니오 — 근거
판정: NOVEL | DIFFERENTIATED | EXISTS
판정 근거: <2~4문장. DIFFERENTIATED면 차별점이 왜 사용자에게 중요한지>
```

## 의미 있는 차별성 기준 (창의성·존재 확인 공통)

**기존에 있는 기능이라도, 아래 중 하나 이상에서 사용자에게 중요한 차별성을 근거와 함께 보이면 창의적인 것으로 인정한다.** 완전히 새로운 메커니즘만 창의적인 것이 아니다.

| 차별성 유형 | 예 |
|---|---|
| 대상 | 기존 앱이 놓친 사용자군(고령자, 특정 직업, 장애, 특정 생활 국면)에 맞춰 다시 설계해 그들이 실제로 쓸 수 있게 됨 |
| 상황·타이밍 | 같은 기능을 다른 순간·장소·맥락에 배치해, 기존 앱이 있어도 쓰이지 않던 순간에 쓰이게 함 |
| 결합·흐름 | 따로 흩어진 기능·데이터를 하나의 흐름으로 묶어, 이전엔 여러 앱을 오가야 하거나 아예 안 되던 일을 가능하게 함 |
| 마찰 제거 | 입력·설정·판단 단계를 자동화(센서, 연동, 기본값)로 구조적으로 없애 사용 빈도·지속률이 달라짐 |
| 국내 적용 | 한국 제도·공공 데이터·국내 서비스와 연동하거나 국내 규칙을 반영해, 해외 앱으로는 안 되는 일을 해냄 |
| 모델·유통 | 같은 기능이라도 비용 구조, 누가 돈을 내는지, 퍼지는 경로가 달라 기존 앱이 닿지 못한 사람에게 닿음 |

차별성으로 인정하지 않는 것: 디자인·UI만 다름, "AI를 붙였다"만 있고 위 유형에 해당하지 않음, 단순 번역·현지화, 방치된 경쟁 앱이 있다는 사실.

## 판정 기준
- `EXISTS`: 같은 대상·같은 상황에서 같은 방식으로 이미 제공되고 있고, 위 차별성 유형 어디에도 해당하지 않음.
- `DIFFERENTIATED`: 유사 기능이 있더라도 위 차별성 유형 중 하나 이상에 해당하고, 그 차별점이 사용자에게 왜 중요한지 근거(장면, 데이터, 리뷰 불만 등)로 보일 수 있음. 판정 근거에 **어떤 유형인지 명시**한다.
- `NOVEL`: 핵심 메커니즘 자체가 같은 앱을 찾지 못함.
- 유사 앱이 방치됐거나 리뷰가 적다는 사실은 차별점이 아니다(수요가 약하다는 신호일 수 있으니 기록해 심사위원에게 전달).
- 차별점을 위 유형 중 어디에도 대지 못하면 EXISTS로 판정한다.
