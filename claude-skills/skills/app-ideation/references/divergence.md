# 심층 발산 절차 (D1~D6)

배경: 초기 3회 실행에서 존재 확인 후보 18개 중 15개가 `EXISTS`였다. 원인은 "누구나 겪는 생활 불편"을 책상에서 떠올렸기 때문이다. 그런 문제는 이미 누군가 앱으로 만들었다.
남이 아직 못 만든 앱은 **좁은 도메인의 실제 불평**이나 **최근 새로 열린 가능성**에서 나온다. 이 절차는 그 두 곳을 반드시 파게 만든다.

모든 단계의 결과(도메인, 검색 쿼리, 페인 포인트와 출처, 후보 15개, 제거 사유, 사전 검색 결과)를 기획서 또는 no-pass 문서의 "발산 기록" 섹션에 남긴다.

---

## D1 — 도메인 선정

아래 풀에서 `index.md`의 "탐색 도메인 기록"상 **최근 10회 안에 쓰지 않은** 도메인 1개를 고른다. 풀에 없는 좁은 도메인을 새로 정의해도 된다 (넓은 도메인 금지: "육아", "건강", "여행"은 너무 넓다).

**직업·현장**
- 택배·배달 기사의 하루 / 요양보호사·방문간호 / 학원 강사·과외 교사 / 소상공인 1인 카페 사장 / 건설 현장 작업자 / 프리랜서 촬영·영상 외주 / 대리운전 / 편의점 야간 알바 / 미용사·네일리스트 / 공인중개사 사무소 / 어린이집 교사 / 농촌 고령 농업인
**삶의 국면**
- 군 복무 중·전역 직후 / 해외 유학생의 한국 생활 / 은퇴 직후 1년 / 투병 중 가족 간병(특정 질환: 투석, 항암 등) / 청각장애인의 일상 / 시각장애인의 장보기 / 1형 당뇨 아이 부모 / 반려동물 노령기·호스피스 / 이혼 후 공동양육 / 다문화 가정 부모
**활동·취미 깊이**
- 러닝 크루 운영 / 동호회 총무 / 텃밭·주말농장 / 캠핑카·차박 / 낚시 / 보드게임 모임 / 아마추어 밴드 / 등산 후 하산길 / 재봉·뜨개질 / 홈베이킹 판매
**최근 열린 가능성 (기술·제도)**
- 최신 iOS/Android 신규 API(온디바이스 AI, Live Activities, 위젯 상호작용, 위성 메시지, UWB 등) / 신규 공공데이터 API(공공데이터포털 최근 등록) / 2025~2026년 시행 법·제도 변화(돌봄, 주거, 노동, 의료) / 새로운 하드웨어 보급(스마트링, 워치 혈압 등)

## D2 — 현장 조사 (웹 검색 ≥ 5회, 필수)

고른 도메인에서 다음을 검색한다. 최소 5회, 그중 2회 이상은 **사람들의 실제 불평**이 나오는 곳을 겨냥한다.
- 커뮤니티 불평: `"<도메인> 불편" site:clien.net`, `<도메인> 힘든점 블라인드`, `<도메인> 맘카페 고민`, `reddit <domain> "is there an app"`, `reddit <domain> "I wish"`, 도메인 전문 카페·포럼
- 기존 앱의 나쁜 리뷰: 해당 도메인 대표 앱의 1~2점 리뷰에서 반복되는 불만
- 새로 열린 것: `<도메인> 2026 제도 변경`, `<도메인> 신규 API`, `iOS 26 new API <관련 기능>`
- 업무 도구 현실: 현장에서 아직 종이, 엑셀, 단톡방, 전화로 하는 일

산출물: **출처(URL 또는 검색어)가 붙은 페인 포인트 10개 이상**. 각 페인 포인트에 "얼마나 자주 겪는가"(매일/주간/월간/드묾)를 표시한다.

## D3 — 발산 15개

페인 포인트를 아래 기법 중 **서로 다른 3가지 이상**과 결합해 후보 15개를 만든다.
각 후보 형식: `이름 — 한 줄 요약 | 누가·언제·불편 | 핵심 통찰 | 근거 페인 포인트 번호 | 기법`

**핵심 통찰** = "기존 해결책(앱·종이·단톡방)이 왜 실패하는가" + "이 앱이 쓰는 비자명한 지렛대". 예: "근무표 공유 앱은 많지만 *가족*이 아니라 *동료*용이라서, 자는 사람을 깨우는 건 가족이다 → 근무표 사진 1장으로 가족 위젯에 '지금 자는 중' 표시".

기법:
1. **하루 마찰 일기** — D1 도메인 사람의 하루를 시간대별로 따라가며 마찰 순간을 찾는다.
2. **센서 × 상황** — 모바일 기능(GPS, 가속도계, 기압계, 카메라, 마이크, NFC, BLE/UWB, 걸음 수, 알림, 위젯, 잠금화면, Live Activity, 단축어, 워치) × 도메인 상황.
3. **오프라인 행동 디지털화** — 아직 종이·기억·단톡방·엑셀로 하는 일.
4. **역발상** — 전제를 뒤집는다 (더 쓰게 → 덜 쓰게, 개인 → 함께/당번제, 기록 → 잊게, 본인 → 대리인/보호자용).
5. **제약 강제** — 화면 없이, 하루 10초, 입력 0, 오프라인 전용, 버튼 1개, 장갑 낀 손으로.
6. **이웃 분야 이식** — 한 분야의 검증된 메커니즘을 다른 분야로 (게임 스트릭, 물류 추적번호, 항공 체크리스트, 병원 인수인계 SBAR, 주식 알림 등).
7. **최근 변화 활용** — D2에서 찾은 새 API·제도·하드웨어가 처음으로 가능하게 만든 것.
8. **불평의 반대편** — 불평하는 사람이 아니라 *불평을 듣는 쪽*(사장, 교사, 보호자)의 문제를 푼다.

## D4 — 뻔함 제거

다음에 해당하면 제거하고 사유를 한 줄로 기록한다.
- 이 도메인을 모르는 사람도 30초 안에 떠올릴 아이디어
- 사용 빈도가 구조적으로 낮음 (몇 년에 한 번, 며칠만 쓰는 이벤트형). 단, 드물어도 겪을 때 피해가 매우 큰 경우는 예외로 남기고 이유를 적는다.
- 핵심 통찰이 "더 편하게/AI로/한 앱에 모아서"뿐인 것
- `index.md` 파이프라인·탈락 후보와 같은 문제 + 같은 메커니즘

최소 8개를 남긴다. 모자라면 D2를 추가로 검색하고 D3을 더 한다.

## D5 — 빠른 사전 검색 (후보당 2회)

남은 후보마다 한국어 1회 + 영어 1회 검색으로 "핵심 메커니즘이 같은 앱"이 바로 나오는지 본다.
- 바로 나오면 `사전 EXISTS`로 제외하고 앱 이름을 기록한다.
- 이 단계는 본 존재 확인(`existence-check.md`)을 **대체하지 않는다**. 본 존재 확인의 6개 후보 한도를 아끼기 위한 필터일 뿐이다.

## D6 — 상위 3개 선정

사전 검색을 통과한 후보 중 아래 3가지를 각각 1~3점으로 매겨 곱이 높은 순으로 상위 3개를 고르고, 다음 순위 3개를 예비로 둔다.
- 통찰 강도: 기존 해결책의 실패 원인을 정확히 찌르는가
- 사용 빈도: 매일/주간 = 3, 월간 = 2, 드묾 = 1
- 모바일 고유성: 모바일이 아니면 안 되는가

## 좋은 후보의 신호
- 문제를 겪는 순간이 구체적이다 ("투석 끝나고 귀가하는 택시 안에서")
- 실제 불평의 출처가 있다
- 한 문장으로 설명하면 그 도메인 사람이 "아 그거 필요했어"라고 하고, 도메인 밖 사람은 "그런 문제가 있는 줄 몰랐네"라고 한다
- 첫 사용까지 설정이 1분 이내로 상상된다
