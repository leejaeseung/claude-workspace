# 파이프라인: 상태, 단계, 선택·전이 규칙

## index.md 파이프라인 표 형식

```markdown
## 파이프라인

| 앱 | 문서 | 상태 | 단계 | 버전 | 점수 이력 | 정체 | 마지막 갱신 | 다음 과제 |
|---|---|---|---|---|---|---|---|---|
| 지금1위 | [jigeum-1wi.md](jigeum-1wi.md) | ACTIVE | 1 | v2 | 3.6 → 3.9 | 0 | 2026-11-23 | 수익 구조 검증 실험 설계 |
```

- **상태**: `ACTIVE`(계속 업그레이드) · `DONE`(단계 4 완료, 업그레이드 중지) · `DROPPED`(재평가 결과 중단, 사유는 실행 로그에)
- **점수 이력**: 매 심사의 6명 평균을 화살표로 누적
- **정체**: 연속으로 의미 있는 개선(평균 +0.2 이상 또는 단계 승급)이 없었던 업그레이드 횟수

## 단계 (업그레이드 1회당 최대 1단계 승급)

| 단계 | 이름 | 이 단계를 마치려면 문서에 있어야 하는 것 |
|---|---|---|
| 0 | 보완 필요 | 아이디어 개요. 심사에서 미달이었지만 유망 |
| 1 | 컨셉 검증 | 통과 기준 충족. 문제·해결책·차별점·핵심 비판 대응 |
| 2 | 사용자 경험 설계 | 핵심 사용자 흐름(첫 실행 → 첫 가치 → 반복 사용), 화면 목록과 화면별 핵심 요소, 리텐션 계기 설계, 엣지 케이스 |
| 3 | 기술·사업 설계 | 기술 아키텍처(클라이언트/서버/외부 API/OS 권한), 데이터 모델, 개인정보 처리 방침 초안, 수익 모델과 단위 경제 추정, 첫 1,000명 확보 계획 |
| 4 | 실행 준비 | MVP 백로그(우선순위·주 단위 일정), 만들기 전 검증 실험 2개 이상의 구체 설계(가설·지표·성공 기준), 랜딩 페이지 카피, 출시 체크리스트 |

## 선택 규칙 (UPGRADE 대상 고르기)

1. 후보: 상태 `ACTIVE`인 기획
2. 정렬: 단계 0보다 단계 ≥1 우선 → 최근 평균 점수 높은 순 → 마지막 갱신이 오래된 순
3. 1건만 선택

## 상태 전이 규칙 (업그레이드 재심사 후)

`prev` = 직전 수락된 버전의 평균, `now` = 이번 평균, `pass` = 통과 기준(KILL 0, 평균 ≥ 3.5, creativity·user-reality ≥ 3) 충족 여부

| 조건 | 결과 |
|---|---|
| 유효한 KILL ≥ 1, 또는 `now` < 3.0 | **DROPPED** — 나빠진 기획은 키우지 않는다 |
| `pass` 이고 `now` ≥ `prev` − 0.2 | **승급**: 새 버전 수락, 단계 +1 (단계 4 완료 시 **DONE**). `now` ≥ `prev` + 0.2 또는 단계 승급이면 정체 0 |
| `pass` 이지만 `now` < `prev` − 0.2 | **유지**: 이번 수정을 되돌리고 직전 버전 유지, 정체 +1 |
| 단계 0에서 `pass` | 단계 1로 승급 (컨셉 검증 완료) |
| `pass` 아님, 3.0 ≤ `now` < 3.5, KILL 0 | **유지**: 이번 수정 중 유효한 개선만 반영, 단계 유지, 정체 +1 |
| 정체 ≥ 2 | **DROPPED** (정체) — 두 번 연속 나아지지 않으면 다른 앱에 시간을 쓴다 |
| 단계 0 상태로 업그레이드 2회 실패 | **DROPPED** |

DROPPED된 기획은 탈락 후보 목록에도 한 줄 추가해 이후 NEW 모드에서 같은 아이디어가 다시 나오지 않게 한다.
DONE된 기획은 사용자가 요청하면(`--upgrade <slug>`) 다시 `ACTIVE`로 되돌릴 수 있다.
