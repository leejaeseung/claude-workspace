# UPGRADE 모드 절차

대상 기획서 `OUT/<slug>.md`와 index.md의 해당 행을 읽고 시작한다.

## U1 — 진단

직전 심사 결과(기획서의 "비판 검증 결과" 섹션)에서 다음을 뽑아 작업 메모에 적는다.
- 해소해야 할 비판 Top 3: KILL/REVISE 사유, 점수가 가장 낮은 역할의 `TOP_CRITICISMS`와 `WHAT_WOULD_CHANGE_MY_MIND`
- 이번 단계 목표: `pipeline.md`의 단계 표에서 현재 단계의 **다음 단계** 산출물 (단계 0이면 "통과 기준 충족"이 목표)
- 이번에 바꾸지 않을 것: 이미 심사위원들이 강점으로 인정한 부분

## U2 — 개선

- 각 비판에 대해 **기획 자체를 바꾸는** 대응을 한다 (타겟 좁히기, 핵심 기능 교체, 사용 계기 재설계, 데이터 수집 축소 등). "그렇지 않다"는 반박만으로는 해소로 치지 않는다.
- 비판이 근본적이라 해소가 불가능하다고 판단되면, 억지로 고치지 말고 그 판단을 기록하고 U4로 가서 심사위원의 평가를 받는다 (중단 여부는 규칙이 정한다).
- 다음 단계 산출물을 작성한다. 분량보다 구체성: 화면은 실제 요소 이름, 수치는 근거, 실험은 성공 기준까지.
- 웹 검색으로 필요한 사실(API 존재 여부, 정책, 시장 수치)을 확인하고 출처를 남긴다.

## U3 — 존재 재확인 (필수)

`existence-check.md` 절차를 따르되:
- 최소 6개 쿼리, 그중 **최소 3개는 이전 버전 기록에 없는 새 쿼리** (바뀐 기능·타겟, 새 대체 표현, 최근 출시 키워드 "2026" 등)
- 이전에 발견한 주요 경쟁자의 최근 변화(새 기능 추가 여부)도 확인
- 판정이 `EXISTS`로 바뀌면 U4를 하지 않고 바로 **DROPPED** (사유: 경쟁자 등장/발견)

## U4 — 재심사 (필수)

`review-panel.md`의 심사위원 6명을 새 에이전트로 병렬 실행한다. 후보 블록에 다음을 **추가**로 넣는다:

```
[업그레이드 정보]
현재 단계 → 목표 단계:
직전 버전 평균 점수와 역할별 점수:
직전 버전 핵심 비판 Top 3:
이번 버전에서의 대응 (비판별):
이번에 새로 작성한 산출물 요약:
```

그리고 공통 지침 끝에 다음 문장을 추가한다:
```
직전 비판이 실제로 해소됐는지 판정하세요. 말로만 대응했거나, 대응 과정에서 새 문제가 생겼다면 반드시 지적하세요.
이번 단계 산출물(사용자 흐름/설계/실행 계획)의 구체성과 현실성도 당신의 역할 관점에서 평가하세요.
출력에 RESOLVED: <직전 비판별 해소 여부 (해소/부분/미해소)> 항목을 추가하세요.
```

## U5 — 판정

`pipeline.md`의 상태 전이 규칙을 기계적으로 적용한다. 메인 에이전트의 애착으로 규칙을 바꾸지 않는다.

## U6 — 기록

- **승급**: 기획서 본문을 새 버전으로 갱신, 새 단계 섹션 추가, 비판 검증 결과를 이번 심사로 교체, "버전 이력"에 한 줄(버전 | 날짜 | 단계 | 평균 | 핵심 변경 | 해소된 비판 | 남은 리스크).
- **유지**: 본문은 직전 버전 유지(유효한 개선만 반영), 버전 이력에 "시도 실패" 줄 추가와 이유, 정체 +1.
- **DROPPED**: 기획서 맨 위에 `> ⛔ 중단 (YYYY-MM-DD): <사유>` 배너 추가, 버전 이력에 최종 줄, index.md 상태 변경, 탈락 후보 목록에 추가. 이어서 같은 실행에서 NEW 모드 수행.
- **DONE**: 기획서 맨 위에 `> ✅ 실행 준비 완료 (YYYY-MM-DD)` 배너, index.md 상태 변경.
