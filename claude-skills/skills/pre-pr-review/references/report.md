# 심각도 기준과 리포트 템플릿

## 심각도 기준 (실제 영향 기준, 코드 모양 기준 아님)

| 심각도 | 기준 | 예시 |
|---|---|---|
| 🔴 **Blocker** | 머지하면 안 됨. 데이터 손실/오염, 보안 취약점, 장애, 핵심 기능이 동작 안 함, 빌드/테스트 실패, 롤백 불가 마이그레이션 | 인가 누락, 트랜잭션 밖 이중 결제, NPE로 핵심 경로 크래시 |
| 🟠 **Major** | 머지 전 수정 권장. 특정 조건에서 잘못된 결과, 중요한 경로의 테스트 부재, breaking change 미고지, 확장 시 확실한 성능 문제 | 빈 목록에서 잘못된 합계, 에러 삼킴, N+1 쿼리 |
| 🟡 **Minor** | 이번 PR 또는 후속으로 수정. 드문 엣지 케이스, 유지보수성 저하, 오해 소지 있는 이름 | 오래된 주석, 부정확한 에러 메시지 |
| ⚪ **Nit** | 선택 사항 | 사소한 명명, 구조 취향 (규약 근거가 있을 때만) |
| ❓ **Question** | 의도 확인 필요. 버그인지 의도인지 코드만으로 판단 불가 | "이 경우 null 반환이 의도인가요?" |

PLAUSIBLE 판정은 전제 조건이 현실적이지 않으면 한 단계 낮춘다. 여러 렌즈가 독립적으로 같은 문제를 찾았다면 신뢰도를 높게 표시한다.

## 리포트 템플릿

```markdown
# Pre-PR 리뷰: <브랜치명> → <base>

**판정: 🔴 BLOCK | 🟠 CHANGES REQUESTED | 🟢 READY**
<판정 이유 한두 문장>

| Blocker | Major | Minor | Nit | Question |
|---|---|---|---|---|
| n | n | n | n | n |

**범위**: 커밋 N개, 파일 N개 (+A / −D), 미커밋 변경 포함 여부
**추정한 의도**: <1~3문장>
**실행한 리뷰**: 렌즈 <목록> · 검증 에이전트 N개 · 모드 <quick|standard|deep>

## 기계적 검증
| 항목 | 명령 | 결과 |
|---|---|---|
| 빌드/타입 | `...` | ✅ / ❌ / ⏭ 실행 안 함(이유) |
| 린트 | | |
| 테스트 | | 통과 n / 실패 n (base에서도 실패: n) |

## 🔴 Blocker

### B1. <제목>
- **위치**: `path/file.ext:123`
- **문제**: <무엇이 왜 잘못됐나>
- **실패 시나리오**: <입력/상태> → <결과>
- **근거**: <코드 경로, 인용>
- **검증**: CONFIRMED (재현: yes — <방법>) · 발견 렌즈: correctness, tests
- **수정안**:
  ```lang
  ...
  ```

## 🟠 Major
### M1. ...

## 🟡 Minor
- `path:line` — <한 줄 요약> → <수정 방향>

## ⚪ Nit
- `path:line` — ...

## ❓ 질문 (작성자 확인 필요)
- `path:line` — ...

## 누락된 테스트 제안
- <테스트 케이스> — <막아주는 버그>

## 기존 문제 (이번 PR 범위 밖)
- `path:line` — <요약> (후속 이슈 권장)

## 검증하지 못한 것
- <실행 못 한 검사, 리뷰 못 한 파일/영역, 런타임 의존으로 판단 불가한 부분과 이유>

<details><summary>검토 후 기각된 지적 (n개)</summary>

- <원 지적 요약> — 기각 근거 `path:line`
</details>
```

## 작성 규칙

- 지적은 심각도 → 같은 심각도 안에서는 영향 범위 순으로 정렬.
- Blocker/Major는 반드시 실패 시나리오와 수정안을 포함. Minor 이하는 한 줄.
- 판정이 READY여도 "검증하지 못한 것"이 크면 판정 옆에 "(조건부)"를 붙이고 이유를 적는다.
- 해당 항목이 없는 섹션은 "없음"으로 남기지 말고 섹션 자체를 생략한다. 단 "검증하지 못한 것"은 항상 유지.
