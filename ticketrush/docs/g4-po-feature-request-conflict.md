## 1. 갈등 발생 배경

### PO 요청 (2026-06-15)

> *"W6에 좌석 즐겨찾기 기능을 추가할 수 있을까요? 유저 리서치에서 '다음 예매 시 선호 좌석 자동 선택' 요청이 많이 나왔어요. 개발 공수는 미드레벨(강민서) 3일 정도?"*

PO가 기능 추가를 요청하는 이유:
- 유저 리서치 결과 "선호 좌석 즐겨찾기" 기능이 Top 3 요청 항목
- W7~W8이 성능/런북/발표 준비로 꽉 차 있어 W6 밖에 기회가 없다고 판단

### 박지훈의 입장

W6는 성능 튜닝 스프린트다. 현재 미달성 지표가 있다:

| 지표 | 목표 | W5 측정값 | 상태 |
|------|------|----------|------|
| seat-api P99 | < 800ms | 312ms | ✅ |
| Consumer lag 피크 | < 5,000건 | 7,200건 | ❌ (조치 완료, 재측정 필요) |
| GC pause P99 | < 10ms | 3.2ms | ✅ |
| E2E P95 | < 5,000ms | 1,104ms | ✅ |

consumer lag 목표가 아직 재측정으로 확인되지 않았다. W6는 이 검증과 Kafka 파티셔닝 재조정에 집중해야 한다.

## 2. 갈등 조율 프로세스 v1 적용

### 단계 1 — 사실 분리

| 항목 | PO | 박지훈 |
|------|-----|--------|
| 주장 | W6에 즐겨찾기 기능 추가 | W6는 성능 튜닝 전용 |
| 근거 | 유저 리서치 Top 3 요청, W6 밖엔 기회 없음 | Consumer lag 미검증, Kafka 파티셔닝 재조정 미완 |
| 불확실 영역 | W6에 기능 추가 시 성능 목표에 미치는 영향 | 기능 추가 공수 정확도 (3일 맞나?) |

### 단계 2 — 데이터 수집 합의

박지훈이 기술 언어를 비즈니스 언어로 번역:

> *"Consumer lag 7,200건 = seat-api가 좌석 잠금 이벤트를 처리하는 데 최대 95초 지연 = 사용자가 결제 완료 후 96초 동안 좌석 상태가 업데이트되지 않는 경우 발생 가능 = 콘서트 오픈 순간 동시 접속 300명 중 일부가 '이미 팔렸는데 여전히 예매 가능하게 보이는' 버그 가능성.*
>
> *P99 800ms = 결제 단계에서 1,000명 중 10명이 0.8초 이상 대기. 현재 312ms로 목표 달성. 그러나 consumer lag 재측정이 남아 있다."*

**합의 기준**:
```
W6 종료 시점(2026-06-21)까지 consumer lag < 5,000건 달성 확인 가능 여부:
- 가능 → 기능 추가 공수 검토 가능 (W7 슬롯 확보 검토)
- 불가 → W6 성능 튜닝 전념, 기능은 W8 이후
```

### 단계 3 — 협상 과정

**W6 Day 1 (2026-06-15) 박지훈 → PO**:

> *"즐겨찾기 기능 자체는 좋은 아이디어입니다. 그런데 지금 consumer lag가 목표치를 초과한 상태고, 재측정 결과가 W6 중반(6/18)에 나옵니다. 강민서가 N+1 수정 + lag 재측정 결과 확인에 집중해야 좌석 상태 버그 리스크가 없어집니다. 재측정 결과가 좋으면 W7에 기능 추가 가능성을 같이 검토하겠습니다."*

**W6 Day 2 (2026-06-16) PO → 박지훈**:

> *"알겠어요. 측정 결과 보고 결정하죠. 근데 W7도 장애 시나리오가 있다고 했는데, 그러면 W8에 기능 추가로 가야 하나요?"*

**박지훈 최종 답변**:

> *"W8 last sprint에 즐겨찾기 기능을 1순위로 넣겠습니다. 로직이 단순하고(userId + seatId 저장) 성능 임팩트도 없습니다. 단, W6 성능 지표가 모두 Green이 되는 것이 선제 조건입니다."*

## 3. 결과

**합의 내용** (2026-06-16):

1. **즐겨찾기 기능은 W8으로 연기** — W6 성능 튜닝 전념
2. **조건**: W6 종료 시 consumer lag < 5,000건 재확인 완료
3. **W8 1순위 할당** 박지훈이 W8 스프린트 첫 아이템으로 명시적 약속

**G4 갈등 조율 포인트**:
- 기술 언어(consumer lag) → 비즈니스 언어(사용자 경험)로 번역
- 감정이 아닌 측정 가능한 조건으로 연기 합의
- "W8에 1순위" 명시로 PO의 기능 누락 우려 해소

## 5. W8 즐겨찾기 기능 예비 설계

연기된 기능의 사전 설계를 남겨 W8에 바로 착수할 수 있게 한다.

```
기능명: 좌석 즐겨찾기
도메인: seat-api (또는 별도 favorites-api 검토)
저장소: PostgreSQL (userId, showId, seatNumber, createdAt)
엔드포인트:
  POST /favorites          { userId, showId, seatNumber }
  GET  /favorites?userId=  → seatNumber 목록
  DELETE /favorites/{id}
의존성: 기존 seat-api 스키마 무관 — 별도 테이블

성능 영향: SELECT/INSERT only, Kafka 이벤트 없음 → lag에 무영향
공수 추정: 강민서 2일 (엔티티 + 서비스 + 테스트)
```

*이 설계는 WIP(Work In Progress)이며 W8 착수 시 팀 합의 후 확정한다.*
