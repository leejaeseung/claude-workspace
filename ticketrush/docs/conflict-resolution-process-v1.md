# 갈등 조율 프로세스 v1

**작성자**: 박지훈 (feature-develop 팀 리더)  
**작성일**: 2026-06-08 (W5)  
**분류**: KPI 3 산출물 — 팀 갈등 조율 프로세스 수립 및 공유  
**적용 사례**: G1 (분산락 방식), G2 (Kafka 파티션 키)

---

## 1. 배경

TicketRush 프로젝트 W2~W5 기간 동안 두 건의 기술적 갈등(G1, G2)이 실제로 발생했다.  
두 갈등을 데이터 기반으로 해소하는 과정에서 팀이 공통으로 사용할 수 있는 패턴을 추출했다.  
이 문서는 그 패턴을 "갈등 조율 프로세스 v1"으로 문서화하여 팀에 공유한다.

> **원칙**: 의견을 **사람**이 아닌 **데이터**에 묶는다.  
> 갈등은 억압이나 다수결이 아니라, 측정 가능한 근거로 해소한다.

---

## 2. 프로세스 5단계

### 단계 1 — 사실 분리 (Fact Separation)

**목적**: "누가 틀렸는가"가 아닌 "무엇이 다른가"를 명확히 한다.

| 항목 | 내용 |
|------|------|
| 갈등 당사자 | 각각 누구인가 |
| 각자의 주장 | 기술적 제안 한 줄 요약 |
| 각자의 근거 | 경험, 직관, 외부 사례 |
| 불확실 영역 | 실측 없이 판단 불가한 부분 |

**G1 적용 예시**:
- 강민서: Redis Lua Script → 낮은 레이턴시, 원자성
- 하진우: PostgreSQL SELECT FOR UPDATE → ACID 보장, 단일 진실 공급원
- 불확실 영역: 1,000 RPS 이상에서 실제 레이턴시와 커넥션 풀 동작

---

### 단계 2 — 데이터 수집 합의 (Data Agreement)

**목적**: 어떤 데이터를 수집하면 갈등을 해소할 수 있는지를 양측이 합의한다.

```
IF [측정 지표] 에서 [A안]이 [B안] 대비 [X배/X% 이상] 우위이면 → A안 채택
그 외이면 → B안 채택 또는 재논의
```

**G1 합의 기준**:
```
Redis Lua P99 ≤ DB P99 × 0.5  →  Redis Lua (ADR-001) 재확인
Redis Lua P99 > DB P99 × 0.5  →  재논의
```

**G2 합의 기준**:
```
userId 키: 핫스팟 파티션 발생 건수 > 0  →  orderId 키 채택
논리적 분석: Saga correlation 키 불일치 확인  →  orderId 키 채택
```

> 💡 **팁**: 데이터 수집 전에 "이 결과가 나오면 어떻게 하겠는가"를 먼저 합의한다.  
> 결과를 보고 나서 기준을 바꾸는 행동을 방지한다.

---

### 단계 3 — ADR 작성 (Architecture Decision Record)

**목적**: 갈등의 맥락, 선택지, 결정, 결과를 영구 기록으로 남긴다.

**ADR 필수 항목**:
1. 컨텍스트 (왜 이 결정이 필요한가)
2. 검토한 선택지 (장단점 trade-off 표)
3. 결정 및 근거 (데이터 기반)
4. 결과 및 후속 조치
5. 교훈 (다음에 비슷한 상황이 오면 어떻게 할 것인가)

**G1 ADR**: ADR-001, ADR-005  
**G2 ADR**: ADR-002

---

### 단계 4 — 결정 후 회고 (Post-Decision Retrospective)

**목적**: 결정이 옳았는지, 프로세스가 작동했는지를 확인한다.

**회고 질문**:
- 예측한 결과와 실제 결과가 일치했는가?
- 어느 측의 우려가 더 정확했는가? 왜?
- 패배(?)한 측이 결정 후에도 팀에 기여할 수 있는 방법이 있었는가?
- 다음 번에 이 단계를 더 빠르게 할 수 있는 방법은?

**G1 회고 결과** (2026-06-08, W5):
- 예측(Redis 우위)과 실제(18배 P99 차이) 일치
- 하진우의 우려(감사 로그, ACID)는 설계 단계에서 흡수 → 기여 가치 인정
- 하진우: "데이터가 나오고 나서 납득이 됐다. ADR에 내 우려가 반영되어 있어서 팀 결정으로 받아들일 수 있었다"
- 다음 번 단축 포인트: PoC 환경 셋업 시간 (2일) → 단일 Docker Compose 스크립트 준비 필요

**G2 회고 결과** (2026-06-08, W5):
- 논리적 분석만으로 충분히 해소 (PoC 불필요)
- 박지훈이 의도적으로 1차 의견 보류 → 하진우가 데이터 기반 재제안 → KPI 4 의사결정 위임 확인
- 강민서: "내 제안이 틀렸다기보다 하진우의 근거가 더 무게 있었다. 논리를 따라갈 수 있었다"

---

### 단계 5 — 패턴화 (Pattern Capture)

**목적**: 이번 갈등에서 배운 것을 다음 갈등 해소에 재사용할 수 있도록 명문화한다.

**TicketRush에서 추출한 패턴**:

| 패턴 | 설명 | 적용 맥락 |
|------|------|-----------|
| PoC First | 직관이 충돌하면 먼저 작은 PoC로 데이터를 수집한다 | 성능, 신뢰성 판단 |
| 기준 선합의 | 결과를 보기 전에 판정 기준을 합의한다 | 데이터 해석 분쟁 방지 |
| 패배측 기여 흡수 | 소수 의견의 우려는 설계에 반영한다 | 팀 신뢰 유지 |
| ADR 의무화 | 기술 결정은 반드시 ADR로 기록한다 | 맥락 보존 |
| 위임 먼저 | 리더가 1차 의견을 보류하고 팀원이 결론 내리도록 유도한다 | 팀원 성장 |

## 3. 각 갈등별 요약

### G1 — 분산락 구현 방식 (W2~W5)

| 항목 | 내용 |
|------|------|
| 당사자 | 강민서 (Redis Lua) ↔ 하진우 (PostgreSQL SELECT FOR UPDATE) |
| 쟁점 | 좌석 점유 원자성 vs 감사 로그/ACID |
| 데이터 수집 | k6 1,000 RPS PoC (ADR-005) |
| 결과 | Redis P99 8.3ms vs DB P99 148ms → **Redis Lua 채택 확정** |
| 하진우 우려 흡수 | Redis Sentinel + `SeatChangedEvent`에 감사 필드 추가 |
| 강민서 기여 | 회고에서 결과 직접 발표 (KPI 3 연결) |
| ADR | ADR-001, ADR-005 |

### G2 — Kafka 파티션 키 (W3~W5)

| 항목 | 내용 |
|------|------|
| 당사자 | 강민서 (userId 키) ↔ 하진우 (orderId 키) |
| 쟁점 | 사용자 이벤트 순서 보장 vs 핫스팟 위험 / Saga 일관성 |
| 데이터 수집 | 논리적 분석 (PoC 불필요로 합의) |
| 결과 | Saga correlation 불일치 + 핫스팟 위험 → **orderId 키 채택** |
| 위임 사례 | 박지훈이 1차 의견 보류 → 하진우 명의 ADR-002 작성 (KPI 4) |
| ADR | ADR-002 |
