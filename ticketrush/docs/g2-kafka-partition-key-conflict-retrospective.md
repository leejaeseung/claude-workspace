# G2 갈등 회고 — Kafka order.created 파티션 키 선택

**갈등 분류**: G2  
**발생 시점**: W3 초반 (2026-05-25)  
**당사자**: 강민서(Developer-1) ↔ 하진우(Developer-2)  
**조율 완료**: W3 말 (2026-05-31)  
**관련 ADR**: ADR-002 (파티션 키 결정), ADR-009 (파티션 증설)  
**KPI 연결**: 박지훈 KPI 3(갈등 조율), KPI 4(위임 확장) / 하진우 KPI 1(Kafka 설계 주도)

---

## 1. 갈등 발생 배경

`order.created` Kafka 토픽에 메시지를 발행할 때 파티션 키로 무엇을 사용할 것인지를 두고 두 개발자 간 의견이 충돌했다.

### 강민서 (userId 주장)

> *"같은 사용자의 주문은 순서가 보장되어야 한다고 생각합니다. userId를 키로 쓰면 파티션 내에서 이벤트 순서가 유지됩니다."*

강민서의 근거:
- 사용자 경험 관점에서 본인 주문 이벤트가 순서대로 처리되는 것이 직관적
- FE 미경험으로 인한 BE 이벤트 순서 보장에 대한 높은 민감도
- 단순한 키 선택이라고 생각해 핫스팟 문제를 인지하지 못함

### 하진우 (orderId 주장)

> *"userId를 키로 쓰면 핫스팟이 생깁니다. 콘서트 오픈 순간에 봇이나 특정 사용자가 주문을 반복하면 단일 파티션에 부하가 집중됩니다. payment 토픽과도 키가 달라져 Saga 추적이 복잡해집니다."*

하진우의 근거:
- 핫스팟 리스크: 특정 userId에 요청이 몰릴 수 있음
- `payment.*` 토픽이 이미 orderId 키를 사용 중 → Saga correlation 불일치
- 비즈니스 로직상 사용자 수준 순서 보장이 실제로 필요하지 않음

## 2. 갈등 조율 프로세스 v1 적용

### 단계 1 — 사실 분리

| 항목 | 강민서 | 하진우 |
|------|--------|--------|
| 주장 | userId → 사용자 수준 순서 보장 | orderId → 균등 분산 + Saga 일관성 |
| 근거 | 사용자 경험 일관성 | 핫스팟 방지, payment 토픽 키 통일 |
| 불확실 영역 | 핫스팟이 실제로 얼마나 심각한가? | userId 기반 비즈니스 요구사항이 있는가? |

### 단계 2 — 데이터 수집 합의

박지훈이 팀에 두 가지 질문을 제시했다.

```
Q1. 비즈니스 요건에 "사용자 수준 이벤트 순서 보장"이 명시되어 있는가?
Q2. payment 토픽과 order 토픽의 키가 다를 때 실제로 Saga 구현이 복잡해지는가?
```

**Q1 검토 결과**: 프로젝트 플랜의 비즈니스 SLA는 "동일 좌석 중복 점유 0건, 결제 이중화 0건"이다. 사용자 수준 순서 보장은 요건에 없다. Saga 패턴이 비동기로 각 단계를 처리하므로 순서 보장은 DB 멱등성으로 충분하다.

**Q2 검토 결과**: `payment.confirmed` / `payment.failed` 토픽은 이미 `orderId`를 키로 사용 중이다. `order.created`가 `userId`를 사용하면 소비자가 두 토픽의 이벤트를 조인할 때 파티션 경계를 넘어야 한다. Kafka 스트림 처리에서 이는 불필요한 복잡도를 추가한다.

### 단계 3 — 결정

PoC 없이 논리적 분석만으로 충분한 근거가 확보됐다. 박지훈이 판단을 하진우에게 위임했다.

> *"하진우가 Kafka 설계를 주도하고 있으니 최종 결정도 하진우가 내려줘. 강민서, 하진우의 근거가 더 무겁다는 것에 동의하나?"*

강민서는 핫스팟 리스크와 Saga correlation 불일치 문제를 이해하고 동의했다.

**결정**: `orderId`를 파티션 키로 채택 (ADR-002)

## 3. 후속 경과 — W6 ADR-009

W5 부하 테스트에서 `order.created` 6파티션이 3,000 RPS 지속 구간에서 Consumer lag 급증의 간접 원인으로 분석됐다. 하진우가 독립적으로 파티션 12개 증설을 결정하고 ADR-009를 작성했다.

ADR-009는 박지훈이 G2 의사결정 위임의 연속선상에서 하진우에게 결정권을 준 결과물이다. **파티션 키 결정(ADR-002)부터 파티션 수 결정(ADR-009)까지 Kafka order.created 설계 전체를 하진우가 소유**하게 됐다.

## 4. 팀 학습 포인트

### 강민서의 성장

> *"처음엔 userId 키가 맞다고 확신했는데, 비즈니스 SLA를 직접 읽어보니 사용자 순서 보장이 요건에 없었어요. '직관적으로 옳아 보이는 것'과 '실제 요건에서 필요한 것'을 구분하는 훈련이 됐습니다."*

- Kafka 파티션 설계에서 **비즈니스 요건 우선 확인** 습관 형성
- 하진우와의 기술 토론에서 핫스팟 개념을 실전으로 학습

### 하진우의 성장

> *"내 의견이 맞다는 것을 알면서도 강민서의 주장을 끝까지 들었습니다. '핫스팟이 얼마나 심각할지' 데이터 없이 일방적으로 밀어붙이지 않고, 박지훈이 제시한 두 질문을 통해 논리로 설득했습니다."*

- 의견 충돌 시 논리 제시 방식 개선
- 파티션 증설 결정을 스스로 주도 → KPI 1 달성 기반

### 박지훈의 조율 방식

G2 조율에서 박지훈이 사용한 핵심 기법:

1. **판단을 직접 내리지 않고 질문으로 틀 제공** — "비즈니스 SLA에 있는가?"라는 질문이 결론을 도출했다
2. **결정권 위임** — 하진우가 Kafka 설계의 맥락과 책임을 모두 가져가도록 했다
3. **강민서의 동의 확인** — 결정에 동의하지 않은 채 진행하면 구현에서 마찰이 생긴다
