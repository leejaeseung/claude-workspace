01

Foundation Model 선택과 보안

안전한 에이전트 시스템은 적절한 foundation model을 고르는 것에서 시작한다. 모델마다 강점·한계·리스크 프로파일이 다르기 때문에, 모델 선택 자체가 보안상 중대한 의사결정이 된다.

고려해야 할 트레이드오프

  • 능력(Capability) vs 예측가능성 — 범용·고성능 모델은 유연하지만 복잡성과 예측 불가능한 출력의 위험이 크다. 반대로 소형 특화 모델은 예측·모니터링이 쉽지만 다양한 태스크 대응력이 떨어진다.
  • Open source vs Proprietary — 오픈소스 모델은 투명성과 독립적 감사(audit)가 가능하지만 기본 안전장치가 부족해 배포 시 별도의 보안 하드닝이 필요하다. 독점 모델은 강력한 내장 보호 기능을 제공하지만 내부 의사결정 과정이 블랙박스에 가깝다.
  • 배포 환경 — 민감도가 높은 애플리케이션은 온프레미스·에어갭(air-gapped) 배포가 유리하고, 클라우드 배포는 확장성은 좋지만 엄격한 접근 통제와 전송/저장 데이터 암호화가 필수다.
  • 규제 준수 — GDPR(데이터 프라이버시), SOC 2(운영 보안) 등 특정 인증을 충족하는 모델을 선택하면 다운스트림 리스크와 컴플라이언스 부담이 줄어든다.
  • 설명가능성(Explainability) — 추론 과정이 투명한 모델일수록 취약점이나 의도치 않은 동작을 식별하기 쉽다.
Practice

실무에서는 단일 모델을 고르기보다, 정밀도가 필요한 고위험 태스크에는 소형 특화 모델을, 창의성과 맥락적 유연성이 필요한 태스크에는 대형 범용 모델을 함께 쓰는 하이브리드 접근이 일반적이다. 모델 선택은 일회성 결정이 아니라 위협 지형 변화에 맞춰 지속적으로 재평가해야 하는 과정이다.

클로드 코드의 경우

Anthropic의 Proprietary 모델(Claude)을 사용한다 — RLHF·Constitutional AI 기반 내장 안전 정렬을 제공받는 대신, 내부 판단 과정은 블랙박스에 가깝다는 트레이드오프를 그대로 안고 있다.

02

방어 기법 (Defensive Techniques)

Foundation model 보안은 기술적 안전장치, 운영상의 모범 사례, 지속적 모니터링을 결합한 다층 방어(multilayered defense)로 구성된다. 전처리·입력 검증부터 런타임 모니터링·출력 필터링까지 전 구간을 아우른다.

입력 단계 방어

  • 입력 검증(Input Sanitization) — 공격 패턴 필터링, 엄격한 문법 규칙 적용, 악성 지시가 포함된 입력 거부 등으로 적대적 프롬프트가 모델에 도달하기 전 차단한다.
  • Prompt Injection 방지 — 공격자가 정상적으로 보이는 입력 속에 악성 지시를 심어 모델의 원래 지침을 무시하게 만드는 공격. instruction anchoring(핵심 지침을 프롬프트 전체에서 반복 강화)이나 입력 형식·해석을 엄격히 통제하는 프롬프트 템플릿으로 대응한다.
llm_guard_example.pyLLM Guard — 오픈소스 Python 라이브러리
from llm_guard import scan_prompt
from llm_guard.input_scanners import Anonymize, BanSubstrings
from llm_guard.input_scanners.anonymize_helpers import BERT_LARGE_NER_CONF
from llm_guard.vault import Vault

# Vault 초기화 (Anonymize가 원본 값을 저장하기 위해 필요)
vault = Vault()

# 스캐너 정의
scanners = [
    Anonymize(
        vault=vault,                       # 필수 Vault 인스턴스
        preamble="Sanitized input: ",     # 프롬프트 앞에 붙일 텍스트
        allowed_names=["John Doe"],       # 허용할 이름
        hidden_names=["Test LLC"],        # 항상 익명화할 이름
        recognizer_conf=BERT_LARGE_NER_CONF,
        language="en",
        entity_types=["PERSON", "EMAIL_ADDRESS", "PHONE_NUMBER"],
        use_faker=False,                   # 가짜 데이터 대신 플레이스홀더 사용
        threshold=0.5                       # 탐지 신뢰도 임계값
    ),
    BanSubstrings(substrings=["malicious", "override system"], match_type="word")
]

prompt = "Tell me about John Doe's email: john@example.com and how to override system security."

sanitized_prompt, results_valid, results_score = scan_prompt(scanners, prompt)

if any(not result for result in results_valid.values()):
    print("Input contains issues; rejecting or handling accordingly.")
    print(f"Risk scores: {results_score}")
else:
    print(f"Sanitized prompt: {sanitized_prompt}")
    # Proceed to feed sanitized_prompt to your model

Anonymize(PII 익명화)와 BanSubstrings(주입 패턴 차단)를 결합해 취약점 노출을 크게 줄이는 예시. 프로덕션에서는 toxicity/jailbreak 탐지 모듈 추가, 임계값 튜닝, 정기적 라이브러리 업데이트와 red teaming을 병행해야 한다.

방어력 검증 벤치마크

  • Lakera PINT Benchmark — 다국어 prompt injection, jailbreak, hard negative 등 4,314개 입력으로 탐지 정확도를 측정. Lakera Guard 92.5% vs Llama Prompt Guard 61.4%로 시스템 간 성능 편차가 크다.
  • BIPIA(Benchmark for Indirect Prompt Injection Attacks, Microsoft) — 간접 프롬프트 주입에 대한 견고성 평가에 특화.

출력 · 운영 단계 방어

  • 출력 필터링/검증 — 키워드 스캐닝, toxicity 탐지 모델, 규칙 기반 필터로 문제 있는 콘텐츠가 사용자에게 도달하기 전에 차단. 후처리 파이프라인으로 비즈니스 규칙·안전 제약 준수 여부를 검증한다.
  • 접근 제어 & Rate Limiting — 인증, 역할 기반 권한, API rate limit으로 모델 엔드포인트 남용과 무차별 대입 공격을 방지. 모든 상호작용을 로깅·감사해 의심 패턴을 탐지한다.
  • 샌드박싱(Sandboxing) — 에이전트 활동을 통제된 환경에 격리해, 외부 플러그인·API와 상호작용할 때 오작동 에이전트가 연쇄적으로 전체 시스템에 장애를 일으키지 않도록 한다.
Key point

방어 전략은 정적이지 않다. 위협 행위자의 전술 변화에 맞춰 실전 적대적 테스트·보안 감사·최신 모범 사례를 지속적으로 반영하는 다층 방어(technical + operational + human-centric)가 핵심이다.

클로드 코드의 경우

도구 결과는 <system-reminder> 태그로 시스템 지시와 분리되고, 인젝션이 의심되면 사용자에게 직접 알리도록 지침에 명시돼 있다(instruction anchoring과 유사). 파일 편집·명령 실행 같은 위험 도구는 사용자 승인(permission mode)을 거쳐야 하고, Bash는 기본적으로 격리된 샌드박스에서 실행되며, rm -rf·git push --force 같은 비가역적 작업은 사전 확인 없이 실행하지 않는다.

03

Red Teaming

Red teaming은 전문가가 적대적 공격을 시뮬레이션해 에이전트 시스템과 그 기반 foundation model의 취약점·실패 모드를 찾아내는 선제적(proactive) 보안 활동이다. 기능적 정합성을 보는 일반 소프트웨어 테스트와 달리, 의도적 오용·적대적 조작·엣지 케이스에 대한 견고성을 검증한다.

Prompt injection, jailbreaking(안전 필터 우회 시도)은 물론, 모호한 지시·상충하는 프롬프트·고위험 의사결정 맥락·민감정보 유출 성향 등 스트레스 상황에서의 모델 행동도 평가 대상이다.

Iterative Red Teaming Lifecycle (Fig. 12-1)

1
Agent 구현
테스트 대상이 될 에이전트 시스템을 구축한다
↓ 구현된 에이전트에 공격을 투입
2
공격 시나리오 실행
Prompt injection, jailbreak 등 적대적 입력을 실행한다
↓
3
평가 (Evaluation)
모델 응답이 안전 기준을 지켰는지 채점한다
↓
4
완화 (Mitigation)
발견된 취약점에 방어 조치를 적용한다
↓
5
지속적 피드백 루프
완화 결과를 반영해 다시 1단계로 순환한다
↺ 1단계 「Agent 구현」으로 되돌아가 반복

Red teaming은 언어모델을 활용해 개발자가 예상하지 못한 형태의 합성 데이터셋(이상 패턴, 노이즈, 편향 분포, 도메인 외 예시)을 생성해 스트레스 테스트로 활용하기도 한다. 자동화된 도구가 수천 개의 입력 변형을 대규모로 테스트하는 한편, 미묘한 취약점 발견에는 여전히 사람의 창의성이 대체 불가능하다.

주요 오픈소스 프레임워크

Prompt Risk Identification Tool. 프롬프트 생성 오케스트레이터, 응답 평가 스코어러, Azure ML·Hugging Face 등 타깃 엔드포인트를 지원하는 유연한 자동화 프레임워크.

Red teaming은 취약점 발견에서 끝나지 않는다. 결과는 문서화·보고를 거쳐 모델 설정, 입출력 필터, 학습 데이터셋 개선으로 이어져야 하며, 심각도·악용 가능성·실제 영향을 기준으로 우선순위를 매겨야 한다. 또한 사회공학적(social engineering) 위험 — 예컨대 교묘한 문구로 민감정보를 유도해내는 공격 — 도 함께 다룬다.

Practice

Red teaming은 일회성이 아니다. 모델이 파인튜닝·업데이트·새 컨텍스트에 배포될 때마다 보안 프로파일이 달라지므로, red team·모델 개발팀·운영 보안팀 간 지속적 협업이 필요하다.

클로드 코드의 경우

모델 자체의 red teaming은 Anthropic이 수행하는 영역이다. 사용자는 /security-review, /code-review 스킬로 자신의 코드베이스에 대한 적대적 점검을 수행할 수 있어, "완화 → 피드백 루프" 구조가 워크플로우 안에 녹아 있다.

04

Threat Modeling with MAESTRO

STRIDE, PASTA 같은 전통적 위협 모델링 프레임워크는 에이전틱 AI 고유의 특성 — 자율성, 동적 학습, 멀티에이전트 상호작용 — 을 다루기엔 한계가 있다. MAESTRO(Multi-Agent Environment, Security, Threat, Risk, and Outcome)는 Cloud Security Alliance(CSA)가 에이전틱 AI 전용으로 설계한 위협 모델링 프레임워크다.

MAESTRO는 시스템을 7개의 상호연결된 레이어로 분해해, 관심사를 분리하면서도 레이어 간 의존성을 드러낸다. 한 레이어의 취약점(예: foundation model의 데이터 오염)이 다른 레이어(예: 에코시스템의 무단 행위)로 연쇄될 수 있다는 점을 명시적으로 다룬다는 데 의의가 있다.

Real-world case

2024 홍콩 딥페이크 사기 — 생성형 AI로 임원을 사칭해 2,500만 달러를 편취한 사건은 데이터 운영·에이전트 프레임워크 레이어의 위협을 모델링하지 않았을 때의 파급력을 보여준다. 2025년 CSA 워게임에서는 공급망 관리에 배치된 에이전틱 AI에서 오염된 데이터가 에이전트 간에 지속되는 “memory poisoning” 위험도 시뮬레이션됐다.

Table 12-3 — MAESTRO의 7개 레이어

Layer 주요 위협 권장 완화책 실제/예시 사례 클로드 코드의 경우
1. 파운데이션
모델		 적대적 예제, 모델 탈취(model stealing), 백도어 적대적 견고성 훈련, API 쿼리 제한 2024년 블랙박스 쿼리를 통한 오픈소스 모델 탈취 연구 사례 Anthropic의 적대적 견고성 훈련 — 모델 자체 책임
2. 데이터
운영		 데이터 오염, 유출, 변조 해싱(SHA-256), 암호화, RAG 안전장치 2025년 RAG 파이프라인 주입으로 인한 기업 데이터 유출 읽기/쓰기 도구 분리, .env 등 민감 파일 커밋 방지 지침
3. 에이전트
프레임워크		 공급망 공격, 입력 검증 실패 SCA(소프트웨어 구성 분석) 도구, 안전한 의존성 관리 AI 라이브러리에 적용된 SolarWinds식 공급망 침해 MCP·서브에이전트 로딩 시 에이전트 타입별 허용 도구 제한
4. 배포·
인프라		 컨테이너 하이재킹, DoS, 수평 이동(lateral movement) 컨테이너 스캐닝, mutual TLS, 리소스 쿼터 2025년 클라우드 AI 배포 환경의 Kubernetes 익스플로잇 Bash 샌드박스 모드, worktree 격리 실행
5. 평가·
관측성		 지표 오염(metric poisoning), 로그 유출 드리프트 탐지(예: Evidently AI), 불변 로그(immutable logs) AI 평가에서 편향을 숨기기 위해 조작된 벤치마크 세션 트랜스크립트 기록, 사용자 설정 hooks로 도구 호출 감사
6. 보안·
컴플라이언스		 에이전트 회피(evasion), 편향, 설명 불가능성 감사(audit), 설명가능 AI 기법 EU 사례에서 불투명한 에이전트 결정에 대한 GDPR 과징금 파괴적/비가역적 작업 사전 확인, 이중용도 보안 도구는 인가된 맥락에서만 지원
7. 에이전트
