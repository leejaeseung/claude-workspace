01

Nonparametric Exemplar Learning (비모수 사례 학습)

가장 단순한 Nonparametric 기법. 에이전트가 태스크를 수행하면서 품질 측정값(feedback)을 받고, 그 성공 사례를 저장해 다음 실행에서 few-shot 예시로 활용한다. 모델 파라미터는 전혀 변경하지 않으며, 프롬프트에 예시를 주입하는 것만으로 성능이 크게 향상된다.

Fixed vs. Dynamic Few-Shot (고정 vs. 동적 예시 선택)

Figure 7-1 Fixed vs Dynamic Few-Shot 선택 방식 비교.
왼쪽: 시스템 프롬프트에 고정된 few-shot 예시 삽입  /  오른쪽: 런타임에 벡터 DB에서 가장 관련성 높은 예시를 동적 검색
Fixed Few-Shot
  • 시스템 프롬프트에 하드코딩
  • 변경되지 않음
  • 구현 가장 단순
  • 모든 입력에 동일 예시 노출
  • 예시 수 늘수록 비용·지연 증가
Dynamic Few-Shot
  • 벡터 DB에서 런타임 검색
  • 현재 입력과 가장 유사한 예시 선택
  • 적은 토큰으로 더 높은 관련성
  • Text 또는 Semantic 검색 사용
  • 예시 수가 늘어도 비용 제어 가능

구체적 예시 — 고객 지원 챗봇

동일한 시나리오를 두 방식으로 구현하면서 차이를 비교한다.
상황: 에이전트가 사용자의 환불/배송/계정 문의에 답하는 고객 지원 챗봇이다. 지금까지 수백 건의 성공적인 응답이 DB에 쌓여 있다.

① Fixed Few-Shot (고정 예시) — 하드코딩 방식

시스템 프롬프트에 대표적인 예시 3개를 직접 박아 넣는다. 사용자의 질문이 무엇이든 항상 같은 3개 예시가 노출된다.

Fixed Few-Shot — 시스템 프롬프트 구성 Python 
# 예시 3개가 하드코딩 — 어떤 질문이 와도 동일한 예시 노출
SYSTEM_PROMPT = """
당신은 고객 지원 에이전트입니다. 아래 예시를 참고하여 답하세요.

[예시 1] 환불 문의
사용자: 주문한 상품이 파손되어 도착했어요. 환불 받을 수 있나요?
에이전트: 파손 상품은 수령 후 7일 이내에 사진과 함께 접수해 주시면
          전액 환불 처리해 드립니다. 고객센터(1234-5678)로 연락 주세요.

[예시 2] 배송 지연 문의
사용자: 주문한 지 5일이 지났는데 배송이 안 왔어요.
에이전트: 불편을 드려 죄송합니다. 주문번호를 알려주시면
          배송 현황을 즉시 확인해 드리겠습니다.

[예시 3] 비밀번호 재설정
사용자: 비밀번호를 잊어버렸어요.
에이전트: 로그인 화면 하단의 비밀번호 찾기를 클릭하시면
          가입하신 이메일로 재설정 링크를 보내 드립니다.
"""

def answer_fixed(user_query: str) -> str:
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},   # 항상 같은 3개 예시
        {"role": "user",   "content": user_query},
    ]
    return llm.invoke(messages)

# 계정 잠금 질문 → 관련 없는 환불·배송·비번 예시만 노출됨
answer_fixed("계정이 잠겼어요. 어떻게 해제하나요?")
Fixed의 한계
사용자가 "계정 잠금"을 물어봐도 모델은 환불·배송·비번 예시만 본다. 관련 없는 예시들이 노이즈가 되고, 예시를 늘릴수록 프롬프트 토큰 비용이 선형으로 증가한다.

② Dynamic Few-Shot (동적 예시) — 벡터 DB 기반 동적 검색

과거 성공 응답들을 벡터 DB에 저장해 두고, 사용자 질문이 들어올 때마다 가장 유사한 예시 k개를 런타임에 검색해 프롬프트를 구성한다.

Dynamic Few-Shot — 벡터 DB 저장 & 런타임 검색 Python 
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain_community.vectorstores import FAISS
from langchain_core.documents import Document

embeddings = OpenAIEmbeddings()
llm        = ChatOpenAI(model="gpt-4o")

# 1) 성공 사례를 벡터 DB에 저장 (오프라인 빌드)
past_examples = [
    Document(page_content="Q: 파손 상품 환불 요청\nA: 수령 후 7일 이내 사진 접수 시 전액 환불 처리"),
    Document(page_content="Q: 5일째 배송이 안 왔어요\nA: 주문번호 알려주시면 배송 현황 즉시 확인"),
    Document(page_content="Q: 비밀번호를 잊어버렸어요\nA: 로그인 화면 비밀번호 찾기 클릭 후 이메일로 재설정"),
    Document(page_content="Q: 계정이 잠겼어요\nA: 5회 로그인 실패 시 보안 잠금, 고객센터 본인 인증 후 해제"),
    Document(page_content="Q: 적립 포인트 만료 기간은?\nA: 적립일로부터 1년 후 자동 소멸, 마이페이지에서 확인 가능"),
        # ... 수백 건의 과거 성공 응답이 추가될 수 있음
]
vectorstore = FAISS.from_documents(past_examples, embeddings)

# 2) 런타임: 질문마다 가장 유사한 예시 k=2 검색
def answer_dynamic(user_query: str, k: int = 2) -> str:
    retrieved = vectorstore.similarity_search(user_query, k=k)
    few_shot_block = "\n\n".join(
        [f"[참고 사례 {i+1}]\n{doc.page_content}"
         for i, doc in enumerate(retrieved)]
    )
    system_prompt = (
        "당신은 고객 지원 에이전트입니다. 아래 참고 사례를 바탕으로 답변하세요.\n\n"
        + few_shot_block
    )
    messages = [
        {"role": "system", "content": system_prompt},  # 질문마다 다른 예시!
        {"role": "user",   "content": user_query},
    ]
    return llm.invoke(messages)

# 계정 잠금 질문 → "계정 잠금 해제" 예시가 자동 검색됨
answer_dynamic("계정이 잠겼어요. 어떻게 해제하나요?")
# 포인트 질문 → "포인트 만료" 예시가 자동 검색됨
answer_dynamic("포인트가 언제 사라지나요?")
Dynamic의 핵심
"계정 잠금" 질문에는 계정 잠금 해제 예시가, "포인트 만료" 질문에는 포인트 관련 예시가 자동으로 선택된다. 수백 건의 예시가 쌓여도 프롬프트엔 항상 가장 관련성 높은 k개만 들어간다.

③ 두 방식 비교 요약

항목 Fixed Few-Shot Dynamic Few-Shot
예시 선택 항상 동일한 N개 (하드코딩) 질문과 가장 유사한 k개 (런타임 검색)
구현 복잡도 매우 낮음 — 문자열 상수만 관리 중간 — 벡터 DB 구축 및 임베딩 필요
토큰 비용 예시 수에 비례해 선형 증가 k 고정 → 예시 수 늘어도 비용 일정
관련성 질문과 무관한 예시 노출 가능 항상 높은 관련성 예시 제공
예시 추가 프롬프트 수동 수정 필요 DB에 저장만 하면 자동 반영
적합한 상황 예시 적고 도메인 단순할 때 예시 많고 질문 유형 다양할 때

메모리 뱅크 (Experience Database)

성공 사례들은 영구 저장소(persistent storage)에 저장된다. 각 인터랙션의 컨텍스트, 수행한 액션, 결과, 받은 피드백이 기록되어 마치 인간의 기억처럼 미래 결정을 안내한다. 에이전트는 과거 사례 DB에서 정보를 검색해 새 문제를 해결하고, 솔루션을 현재 상황에 맞게 적응시키며 문제 해결 전략을 지속적으로 정제한다.

1
경험 수집
에이전트가 태스크 수행 → 컨텍스트·액션·결과·피드백을 DB에 저장
2
유사 사례 검색
새 문제 발생 시 메모리에서 유사 과거 사례 탐색 (텍스트/시맨틱 검색)
3
솔루션 적응
과거 솔루션을 현재 상황에 맞게 적응시켜 적용 → 지속적 정제
핵심 포인트
성공 예시를 저장·검색·제공하는 것만으로 다양한 도메인에서 성능이 크게 향상된다는 것은 잘 검증된 발견이다. 단순하고 투명하며 가볍게 에이전트 성능을 빠르게 개선하는 방법이다.
02

Reflexion (자기반성 학습)

Reflexion은 에이전트에게 언어 기반 자기비판(self-critique) 습관을 부여한다. 실패한 시도 후 에이전트가 무엇이 잘못됐는지, 다음엔 어떻게 개선할지를 짧은 반성문으로 작성한다. 이 반성들은 메모리 버퍼에 축적되고, 다음 시도 전에 다시 읽어 전략을 조정한다. 모델 파라미터를 전혀 건드리지 않는다.

핵심 아이디어

Foundation Model을 자신의 코치로 사용한다.
수치 피드백(성공 플래그)과 자유형식 코멘트 모두 수용하며, 코드 디버깅·다단계 추론 등 다양한 태스크에서 성능 향상이 검증됐다.

Reflexion (반성) 루프 — 5단계

1
액션 시퀀스 수행
에이전트가 프롬프트 기반 플래닝으로 환경과 상호작용
2
Trial 로그 기록
모든 단계 — 액션, 관찰, 성공/실패 — 를 영구 저장소(JSON 파일 또는 DB 테이블)에 추가
3
반성문 생성
실패 시: 최근 인터랙션 히스토리 + 질문 템플릿으로 짧은 "reflection prompt" 구성 → "어떤 전략을 놓쳤나? 다음엔 어떻게 해야 하나?" → LLM이 개선 플랜 생성
4
메모리 업데이트
update_memory() 함수가 Trial 로그 읽기 → LLM 호출로 자기비판 생성 → 에이전트의 메모리 구조에 다시 저장
5
다음 실행에 반성 주입
같거나 유사한 태스크 재시도 시, 최근 반성문을 프롬프트 앞에 추가하여 개선된 전략으로 유도
Figure 7-2 Reflexion 에이전트 구조. 실패한 Trial의 로그가 반성 프롬프트로 변환되어 메모리에 저장되고, 다음 실행 시 프롬프트에 주입된다.

Reflexion Prompt (반성 프롬프트)의 3가지 구성 요소

A
프레이밍 지시 (Framing Instruction)
"태스크에 실패했다. 환경을 요약하지 말고 전략적 실수에 집중하라. 'Plan' 뒤에 개선 플랜을 출력하라." → 간결하고 파싱 가능한 응답 보장
B
원래 목표 재진술 (Restated Goal)
"Instruction: 유제품 없는 사과 과자 버라이어티팩, $30 미만"처럼 진짜 목표를 앵커로 사용
C
실패 트랜스크립트 (Full Transcript)
모든 Action/Observation 기록과 STATUS: FAIL을 포함 → "Plan:" 큐로 처방 단계로 전환

구현 코드 — LangGraph + LangChain

Reflexion 핵심 구현 Python 
from typing import List, Dict, Any
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, MessagesState, START
from langchain_core.messages import HumanMessage

llm = ChatOpenAI(model="gpt-5")
reflections = []

# 기본 모델 호출 래퍼
def call_model(state: MessagesState):
    response = llm.invoke(state["messages"])
    return {"messages": response}

# 반성 쿼리 생성 (최근 3개 반성 + 현재 Trial 로그)
def _generate_reflection_query(trial_log: str, recent_reflections: List[str]):
    history = "

".join(recent_reflections)
    return f"{history}
{trial_log}
위 내용을 바탕으로, 다음에는 어떤 계획을 따르겠습니까? 계획:"

# 메모리 업데이트 — 실패한 env_config에만 반성 추가
def update_memory(trial_log_path: str, env_configs: List[Dict[str, Any]]):
    with open(trial_log_path, 'r') as f:
        full_log: str = f.read()
    env_logs: List[str] = full_log.split('#####

#####')
    for i, env in enumerate(env_configs):
        if not env['is_success'] and not env['skip']:
            # 컨텍스트 과부하 방지: 최근 3개 반성만 유지
            memory: List[str] = env['memory'][-3:]
            reflection_query = _generate_reflection_query(env_logs[i], memory)
            reflection = llm.invoke([{"role":"user", "content": reflection_query}])
            env_configs[i]['memory'] += [reflection]

# StateGraph에 reflexion 노드 하나만 추가하면 완성
builder = StateGraph(MessagesState)
builder.add_node("reflexion", call_model)
builder.add_edge(START, "reflexion")
graph = builder.compile()

result = graph.invoke({"messages": [HumanMessage(reflexion_prompt)]})
reflections.append(result)
update_memory(trial_log_path, env_configs)
왜 이게 효과적인가?
  • • 파라미터 변경 없이 LLM이 자신의 코치가 됨
  • • StateGraph에 노드 하나만 추가 → 모든 실행에서 자동으로 전략 정제
  • • 수치 피드백 + 자유형식 코멘트 모두 처리 가능
  • • 코드 20줄 이하로 반복 실행에서 지속적 개선
03

Experiential Learning (경험 기반 학습, ExpeL)

ExpeL은 Reflexion을 한 단계 더 발전시킨다. 에이전트가 경험을 DB에 쌓는 것에서 나아가, 여러 경험으로부터 인사이트를 추출·집약하여 미래 정책을 개선한다. 과거 실패를 반성하고 유사 상황에서 더 잘할 새로운 기법을 발전시키는 데 특히 유용하다.

Reflexion과의 차이

Reflexion: 같은 태스크 내에서 실패 → 반성 → 재시도
ExpeL: 여러 태스크에 걸쳐 인사이트를 추출하고 크로스-태스크 학습 수행
→ 서로 다른 태스크에서도 적용 가능한 일반 원칙(general rules)을 발견

Figure 7-3 Experiential Learning 에이전트 구조. 경험 풀에서 인사이트를 추출하고, 인사이트는 시간이 지남에 따라 promote/demote/edit 된다.

인사이트 운영 4가지 연산 (Insight Operations)

기존 인사이트들은 주기적으로 재평가되어 상대적 중요도가 조정된다:

AGREE

기존 규칙이 태스크에 강하게 관련된다고 판단될 때 유지·동의

REMOVE

기존 규칙이 다른 규칙과 모순되거나 중복·유사할 때 제거

EDIT

기존 규칙이 충분히 일반적이지 않거나 개선 가능할 때 수정

ADD

기존 규칙과 구별되고 다른 태스크에도 관련성 있는 새 규칙 추가

경험 풀 수집 → 성공/실패 쌍에서 인사이트 추출 → 시간이 지남에 따라 promote/demote → 소수의 핵심 인사이트로 압축 → 에이전트 가이드

인사이트 생성 프롬프트 패턴 Prompt 
# 새 인사이트 추출
성공한 시도와 기존 규칙 목록을 대조·검토하여 아래 연산을 수행하세요.
새 규칙 목록은 실패한 시도 또는 제안된 사고 방식에 대한
일반적이고 고수준의 비판이어야 하며,
향후 다른 질문에서 유사한 실패를 방지하는 데 활용될 수 있어야 합니다.

# 각 연산의 출력 포맷
동의(AGREE) <기존 규칙 번호>: <기존 규칙>
제거(REMOVE) <기존 규칙 번호>: <기존 규칙>
수정(EDIT) <기존 규칙 번호>: <새로운 수정된 규칙>

InsightAgent (인사이트 에이전트) 전체 구현

InsightAgent — 인사이트 생성·승격·강등·편집·반성 Python 
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, MessagesState, START
from langchain_core.messages import HumanMessage

llm = ChatOpenAI(model="gpt-5")

def call_model(state: MessagesState):
    response = llm.invoke(state["messages"])
    return {"messages": response}

class InsightAgent:
    def __init__(self):
        self.insights          = []
        self.promoted_insights = []
        self.demoted_insights  = []
        self.reflections       = []

    def generate_insight(self, observation):
        messages = [HumanMessage(content=
            f"다음 관찰 결과를 바탕으로 인사이트 분석을 생성하세요: '{observation}'")]
        builder = StateGraph(MessagesState)
        builder.add_node("generate_insight", call_model)
        builder.add_edge(START, "generate_insight")
        graph   = builder.compile()
        result  = graph.invoke({"messages": messages})
        insight = result["messages"][-1].content
        self.insights.append(insight)
        return insight

    def promote_insight(self, insight):
        if insight in self.insights:
            self.insights.remove(insight)
            self.promoted_insights.append(insight)

    def demote_insight(self, insight):
        if insight in self.promoted_insights:
            self.promoted_insights.remove(insight)
            self.demoted_insights.append(insight)

    def edit_insight(self, old_insight, new_insight):
        for lst in [self.insights, self.promoted_insights, self.demoted_insights]:
            if old_insight in lst:
                lst[lst.index(old_insight)] = new_insight
                return

    def reflect(self, reflexion_prompt):
        builder = StateGraph(MessagesState)
        builder.add_node("reflection", call_model)
        builder.add_edge(START, "reflection")
        graph  = builder.compile()
        result = graph.invoke(
            {"messages": [HumanMessage(content=reflexion_prompt)]})
        reflection = result["messages"][-1].content
        self.reflections.append(reflection)
        return reflection

실전 사용 예시 — KPI 보고서에서 인사이트 학습

InsightAgent 사용 — 마케팅 KPI 학습 시나리오 Python 
agent = InsightAgent()

# 마케팅 KPI 보고서 (텍스트, KPI 달성 여부)
reports = [
    ("웹사이트 트래픽이 15% 증가했으나, 이탈률이 40%에서 55%로 급등했습니다.", False),
    ("이메일 오픈율이 25%로 개선되어 목표치 20%를 초과 달성했습니다.",           True),
    ("장바구니 이탈률이 60%에서 68%로 증가하여 50% 목표를 달성하지 못했습니다.",  False),
    ("평균 주문 금액이 8% 상승하여 5% 상향 목표를 초과 달성했습니다.",     True),
    ("신규 구독 가입 수가 5% 감소하여 10% 성장 목표에 미치지 못했습니다.",     False),
]

# 1) 보고 기간별 인사이트 생성 & 우선순위 조정
for text, hit_target in reports:
    insight = agent.generate_insight(text)
    if hit_target:
        agent.promote_insight(insight)   # 성공 → 승격
    else:
        agent.demote_insight(insight)    # 실패 → 강등

# 2) Human-in-the-loop 편집 — 승격된 인사이트 정제
if agent.promoted_insights:
    original = agent.promoted_insights[0]
    agent.edit_insight(original,
        f"정제됨: {original} 이탈률 감소를 위한 랜딩 페이지 UX 개선 방안을 검토하세요.")

# 3) 최종 인사이트 상태 출력
agent.show_insights()

# 4) 상위 인사이트 기반으로 다음 실험 계획 반성
reflection_prompt = (
    "승격된 인사이트를 바탕으로, 다음 분기에 실행할"
    "고영향력 실험 하나를 제안해 주세요:
"
    f"{agent.promoted_insights}"
)
agent.reflect(reflection_prompt)
비정상 환경 대응
ExpeL의 인사이트 동적 조정 덕분에 비정상적으로 변화하는 환경(nonstationary environment)에도 효과적으로 적응할 수 있다. 에이전트 정책이 바뀌는 환경에 맞춰야 할 때 특히 강력하다.

언제 Fine-tuning으로 넘어갈까?

Nonparametric 방법은 구현이 빠르고 저렴하며 투명하다.
단, 예시·인사이트가 프롬프트에 쌓일수록 비용과 지연이 증가한다.
충분히 많은 샘플이 축적되면 → Fine-tuning을 통해 모델 자체에 지식을 내재화하는 것을 고려하라.
