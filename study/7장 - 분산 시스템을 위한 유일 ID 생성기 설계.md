
auto_increment 속성이 설정된 관계형 데이터 베이스의 기본 키를 쓰면 되지 않을까?
-> 안된다. 데이터베이스 서버 한 대로는 트래픽을 감당할 수 없고, 여러 데이터베이스를 사용한다면 delay 를 낮추기가 매우 힘들다.

# 1단계 - 문제 이해 및 설계 범위 확정

면접관과의 적절한 질문을 통해 모호함을 없애고 설계 방향을 정해야 한다.

ID 의 특성은?
-> 유일하고 정렬 가능해야 함
새로운 레코드의 ID 는 항상 1만큼 큰 값이어야 하나?
-> 언제나 1씩 증가한다고 할 수는 없지만, 항상 증가하는 방향이어야 함.
ID 는 숫자로만 구성되나?
-> 그렇다
시스템의 규모는?
초당 10000 개의 ID 를 생성할 수 있어야 한다.

위 질의응답을 정리하면
- ID 는 유일해야 함
- ID 는 숫자로만 구성
- ID 는 64비트로 표현될 수 있는 값이어야 함
- ID 는 발급 날짜에 따라 정렬 가능해야 함
- 초당 10000 개의 ID 를 만들 수 있어야 함

# 2단계 - 개략적 설계안 제시 및 동의 구하기

분산 시스템에서 유일성이 보장되는 ID 를 만드는 방법은 다음과 같이 여러가지다.

## 다중 마스터 복제

![[Pasted image 20260906122143.png]]
데이터베이스의 auto_increment 를 이용하는 방식이다.
각 서버의 ID 는 데이터베이스 서버의 개수(N)만큼 ID 를 증가시킨다.
즉,
1번 서버에서 채번되는 ID : 1, 3, 5, 7... 
2번 서버에서 채번되는 ID : 2, 4, 6, 8...

이러면 각 서버에서 채번되는 ID 가 겹치지 않아 유일성이 보장된다.

#### 단점
1. ID 의 순서가 ID 채번 순서라는 보장을 할 수 없다. (시간 흐름에 따른 정렬 x)

1번 서버에서 1, 3, 5 채번한 뒤
2번 서버에서 2 채번
실제 생성 순서 : 1 -> 3 -> 5 -> 2

2. 여러 데이터 센터에 걸쳐 규모를 늘리기 어렵다.
3. 서버를 추가하거나 삭제할 때 잘 동작하도록 만들기 어렵다.

auto_increment 의 N 값이 변경될텐데, 각 데이터베이스에 동기화하기 어려울 듯 하다.

## UUID

랜덤한 128 비트의 ID 값
충돌 가능성이 매우 적다.
"중복 UUID 가 1개 생길 확률을 50% 로 끌어올리려면 초당 10억 개의 UUID 를 100년 동안 계속해서 만들어야 한다."

#### 장점
- 서버 사이의 조율 및 동기화가 필요 없다.
- 각 서버가 별도 채번하므로 규모 확장이 쉽다.

#### 단점
- ID 가 128 비트로 길다.
- ID 를 시간순으로 정렬할 수 없다.(UUID v6, v7 를 사용한다면 가능하다)
- ID 가 숫자로만 구성되지 않는다.

## 티켓 서버

![[Pasted image 20260906123412.png]]

auto_increment 를 사용하는 데이터베이스 서버(티켓 서버)를 중앙 집중형으로 사용한다.

#### 장점
- 유일성 보장 및 숫자로만 구성된 ID 를 쉽게 만들 수 있다. (auto_increment)
- 구현이 쉽다.

#### 단점
- 티켓 서버가 병목 지점이 되어 성능이 저하된다.
- 티켓서버가 Single-Point-Of-Failure 가 된다. 티켓 서버에 장애가 생기면 모든 웹 서버가 영향을 받는다.
- 고가용성을 위해 여러 티켓서버를 두면, 데이터 동기화 등의 새로운 이슈가 발생한다.

## 트위터 스노플레이크 접근법

다음과 같은 64비트 ID 구조를 정의하자.
![[Pasted image 20260906123852.png]]

- **사인(sign) 비트 :** 1비트를 할당한다. 지금으로서는 쓰임새가 없지만 나중을 위해 유보해 둔다. 음수와 양수를 구별하는 데 사용할 수 있을 것이다.
- **타임스탬프 :** 41비트를 할당한다. 기원 시각(epoch) 이후로 몇 밀리초가 경과햇는지를 나타내는 값이다. 본 설계안의 경우에는 기원 시각으로 트위터 스노플레이크 구현에서 사용하는 값 1288834974657(Nov 04, 2010, 01:42:54 UTC에 해당)을 이용할 것이다.
- **데이터센터 ID :** 5비트를 할당한다. 따라서 2 = 32개 데이터센터를 지원할 수 있다.
- **서버 ID :** 5비트를 할당한다. 따라서 데이터센터당 32개 서버를 사용할 수 있다.
- **일련번호 :** 12비트를 할당한다. 각 서버에서는 ID를 생성할 때마다 이 일련번호를 1만큼 증가시킨다. 이 값은 1밀리초가 경과할 때마다 0으로 초기화 된다.

# 3단계 - 상세 설계

- 데이터센터 ID 와 서버 ID 는 시스템 시작 시에 결정되므로 운영 중엔 바뀌지 않는다.
  이를 변경 시 ID 충돌이 발생할 수 있으므로 신중해야 한다.
- 41비트의 타임스탬프는 시간이 흐름에 따라 큰 값을 가지므로 ID 는 시간 순으로 정렬이 가능해진다.
  타임스탬프가 동일하고 데이터센터, 서버 ID 가 다르면 정렬이 꼬일 수 있지 않을까?
  -> 타임스탬프. 즉, 밀리초까지 동일하다면 어떻게 정렬되든 크게 상관 없을 수 있다.
- 41비트 타임스탬프의 최댓값을 69년인데, 69년이 지나면 다른 값으로 마이그레이션 해야 한다.
- 일련번호는 12비트로 4096개의 값을 가질 수 있고, 어떤 서버가 같은 밀리초 동안 하나 이상의 ID 를 만들어 낸 경우에만 0보다 큰 값을 갖는다.

## 4단계 - 마무리

- 시계 동기화 : 각 서버의 시계가 모두 같다고 보장할 수 없다. 즉, 동일한 시간이지만 A 서버에서의 타임스탬프와 B 서버에서의 타임스탬프가 다를 수 있다.
- 각 절(section)의 길이 최적화 : 64비트를 애플리케이션 특성에 따라 다르게 쪼갤 수 있다.
  ex) 동시성이 낮고 수명이 길다면 -> 일련번호를 짧게 하고 타임스탬프를 늘린다.
- 고가용성 : ID 생성기는 아주 높은 가용성을 보장해야 한다.
