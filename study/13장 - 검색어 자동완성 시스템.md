### 요구사항
면접관과의 질의응답을 통해 검색어 자동완성 시스템의 아래와 같은 요구사항을 도출하였다.

- **빠른 응답 속도** : 사용자의 검색어 입력에 따른 자동완성 검색어가 충분히 빠르게 제공되어야 한다. (페이스북의 경우 100ms 이내)
- **연관성** : 자동완성된 검색어는 사용자의 입력과 연관된 것이어야 한다. (본문 예시의 경우 문자열 첫 부분 매칭)
- **정렬** : 자동완성 계산 결과는 인기도 등의 순위 모델에 의해 정렬되어야 한다. (본문 예시의 경우 질의 빈도 순)
- **규모 확장성** : 많은 트래픽을 감당할 수 있도록 확장 가능해야 한다.
- **고가용성** : 시스템의 일부에 장애가 발생하거나 문제가 생겨도 시스템을 계속 사용 가능해야 한다.

### 개략적 규모 추정

- 일간 능동 사용자는 천만 명으로 가정
- 사용자 별 평균 10 건 검색을 수행함을 가정
- 질의 시마다 평균 20바이트를 입력한다고 가정
	- 문자 인코딩은 ASCII 가정. 1문자 = 1바이트
	- 질의문은 평균 4개 단어로 구성된다고 가정. 각 단어는 평균적으로 5 글자로 구성된다고 가정
	- 따라서 질의당 평균 20 바이트로 가정
- 검색창에 글자 입력 시마다 백엔드 서버에 요청.
	- 즉, 1회 검색 당 평균적으로 20회 요청
	- ex) dinner 검색 시 d, di, din, dinn, dinne, dinner 총 6개의 요청 발생
- 초당 약 24000 QPS
- 최대 QPS : 24000 * 2 = 48000 QPS
- 질의 중 20% 정도를 신규 검색어라고 가정.
	- (천만 사용자) * (일당 10개 질의) * 20자 * 20% = 0.4GB 의 데이터가 시스템에 추가됨


개략적으로 시스템을 두 부분으로 나눠볼 수 있다.
1. **데이터 수집 서비스** : 사용자의 질의 입력을 실시간으로 수집하는 시스템.
2. **질의 서비스** : 질의에 대한 다섯 개의 인기 검색어를 정렬해 응답하는 서비스.

#### 데이터 수집 서비스
**질의문(query)**과 **빈도 수(frequency)**를 저장하는 빈도 테이블을 정의한다.
동일 질의문이 들어올 때마다 빈도 수를 1 씩 증가시킨다.

#### 질의 서비스
저장된 빈도 테이블의 frequency 기준으로 상위 5개 정렬된 데이터를 응답한다.


대용량 트래픽 환경에서 위 구조는 최적화가 필요하다.
- 트라이(trie) 자료구조
- 데이터 수집 서비스
- 질의 서비스
- 규모 확장이 가능한 저장소
- 트라이 연산

### 트라이 자료구조
**트라이(trie)**는 문자열을 간략하게 저장할 수 있는 트리 형태의 자료구조다. 이름은 "re**trie**val"(찾아내다)에서 따왔으며, **접두어(prefix) 검색**에 최적화되어 있다.

- 루트 노드는 빈 문자열을 나타낸다.
- 각 노드는 글자 하나를 저장하며, 최대 26개(a~z)의 자식 노드를 가질 수 있다.
- 각 노드는 **루트에서 해당 노드까지의 경로가 만드는 문자열**(단어 또는 접두어)을 나타낸다.
- 검색어 자동완성을 위해 각 노드에 해당 검색어의 **빈도 수**를 함께 저장한다.

#### 예시
아래와 같은 빈도 테이블이 있다고 가정하자.

| query | frequency |
| ----- | --------- |
| tree  | 10        |
| try   | 29        |
| true  | 35        |
| toy   | 14        |
| wish  | 25        |
| win   | 50        |

이를 트라이로 표현하면 다음과 같다. (괄호 안은 빈도 수, 빈도가 있는 노드가 실제 검색어)

```
                     (root)
                 /            \
               t                w
            /     \             |
          tr        to          wi
        /  |  \      |        /    \
     tre  tru  try   toy     wis    win
      |    |   (29)  (14)     |     (50)
    tree  true                wish
    (10)  (35)                (25)
```

- `tr` 노드는 `tree`, `true`, `try` 세 검색어가 공유하는 접두어다. 공통 접두어를 한 번만 저장하므로 저장 공간이 절약된다.
- 사용자가 `tr`을 입력하면 `tr` 노드 아래의 서브트리만 보면 된다. 전체 검색어 테이블을 뒤질 필요가 없다.

#### 인기 검색어 k개를 찾는 과정
사용자가 `tr`을 입력하고 상위 2개(k=2)를 요청했다고 하자.

1. **접두어 노드 탐색** : 루트에서 `t` → `tr` 순으로 내려가 접두어 노드를 찾는다. → `O(p)` (p : 접두어 길이)
2. **서브트리 순회** : `tr` 아래의 모든 유효 노드를 찾는다. → `tree(10)`, `true(35)`, `try(29)` → `O(c)` (c : 서브트리 노드 수)
3. **정렬 후 상위 k개 선택** : 빈도 순으로 정렬해 `true(35)`, `try(29)`를 반환한다. → `O(c log c)`

총 시간 복잡도는 `O(p) + O(c) + O(c log c)`이다. 직관적이지만, 최악의 경우 2번에서 트라이 전체를 순회해야 할 수도 있어 대용량 환경에서는 느리다.

#### 최적화
1. **접두어 최대 길이 제한**
	- 사용자가 긴 검색어를 입력하는 경우는 드물다. 접두어 길이를 상수(ex. 50)로 제한하면 1번 단계가 `O(p)` → `O(1)`이 된다.
2. **노드마다 인기 검색어 캐시**
	- 각 노드에 그 노드를 접두어로 갖는 **상위 k개 검색어를 미리 저장**해둔다.
	- ex) `tr` 노드 : `[true:35, try:29]`, `t` 노드 : `[true:35, try:29]`, `w` 노드 : `[win:50, wish:25]`
	- 2, 3번 단계가 필요 없어져 `O(1)`이 된다.
	- 대신 노드마다 캐시를 저장하므로 **저장 공간을 더 쓴다.** 빠른 응답 속도가 중요한 자동완성에서는 감수할 만한 트레이드오프다.

두 최적화를 적용하면 **접두어 노드 탐색**과 **결과 반환(캐싱)** 모두 `O(1)`로 처리할 수 있다.

### 데이터 수집 서비스
모든 사용자 입력마다 트라이를 수정하면, 질의 서비스는 심각하게 느려질 수 있다. (트라이가 만들어진 뒤에 인기 검색어는 자주 바뀌지 않을 것이므로, 트라이를 자주 갱신할 필요는 없다)
따라서 **분석 서비스** 혹은 **로깅 서비스**로부터 데이터를 취합해 트라이를 갱신해야 한다.

- **데이터 분석 서비스 로그** : 검색창에 입력된 질의에 대한 정보를 로그성으로 append 한다. (수정 x)
- **로그 취합 서버** : 로그 데이터를 취합하는 서비스. **실시간성 요구사항**에 따라 취합 주기를 조절해야 한다.
- **취합된 데이터** : 특정 주기로 질의문(query)에 대한 frequency 를 집계한 테이블.
	![[Pasted image 20261006213115.png|316]]
- **작업 서버** : 주기적으로 트라이 데이터베이스를 업데이트하는 서버들
- **트라이 캐시** : 분산 캐시 시스템. 주기적으로 트라이 데이터베이스의 스냅샷으로 캐싱한다.
- **트라이 데이터베이스** : 트라이 데이터를 영속시키는 저장소. document 저장소나, key-value 저장소(해시 테이블)를 사용할 수 있다.
	- **key-value 저장소(해시 테이블) 활용 예시**
		- 트라이의 각 노드를 해시 테이블의 한 항목으로 변환한다.
			- **key** : 노드가 나타내는 **접두어**
			- **value** : 해당 노드에 캐시된 **인기 검색어와 빈도 목록**
		- 아래 그림은 `be:15`, `bee:20`, `beer:10`, `best:35` 네 개의 검색어가 담긴 트라이를 해시 테이블로 옮긴 모습이다.
		![[Pasted image 20261006213146.png]]
		- 트라이의 노드 6개(`b`, `be`, `bee`, `bes`, `beer`, `best`)가 해시 테이블의 항목 6개가 된다.
			- `b` → `[be:15, bee:20, beer:10, best:35]`
			- `be` → `[be:15, bee:20, beer:10, best:35]`
			- `bee` → `[bee:20, beer:10]`
			- `bes` → `[best:35]`
			- `beer` → `[beer:10]`
			- `best` → `[best:35]`
		- 사용자가 `be`를 입력하면 루트부터 트리를 탐색할 필요 없이 `get("be")` 한 번으로 결과를 얻는다. → `O(1)`
		- 노드에 캐시된 값을 그대로 펼친 형태이므로, **트라이의 노드 수만큼 항목**이 생긴다.

### 질의 서비스
![[Pasted image 20261006213418.png]]
1. 검색 질의가 로드밸런서로 전송
2. 로드밸런서는 해당 질의를 API 서버로 요청
3. API 서버는 트라이 캐시에서 응답을 바로 구성.
4. 캐시에 존재하지 않는 경우엔 트라이 데이터베이스를 기준으로 응답 구성 및 캐시 write (look aside)

#### 최적화 방안
- **AJAX 요청** : 웹 애플리케이션은 AJAX로 자동완성 결과를 요청한다. 페이지를 새로고침하지 않고 비동기로 결과를 주고받을 수 있다.
- **브라우저 캐싱** : 자동완성 결과는 짧은 시간 안에 잘 바뀌지 않으므로, 응답을 브라우저 캐시에 저장해 같은 접두어는 서버에 다시 요청하지 않는다.
	- ex) 구글은 `Cache-Control: private, max-age=3600` 헤더로 결과를 1시간 동안 사용자 브라우저에만 캐시한다.
- **데이터 샘플링** : 모든 질의를 로깅하면 CPU·저장 공간 소모가 크다. N개 요청 중 1개만 로깅하는 식으로 샘플링해 비용을 줄인다.

## 트라이 연산

#### 트라이 생성
작업 서버가 주기적으로 로그 혹은 데이터베이스로부터 취합한 데이터를 트라이로 저장한다.

### 트라이 갱신
아래와 같이 2가지 방법이 있다.

1. 주기적으로 새로운 트라이를 만들어 기존 트라이를 대체
2. 트라이의 각 노드를 개별적으로 갱신. (하나의 트라이 노드에 대한 모든 상위 노드들을 갱신해야 하므로 성능이 좋지 않다.)

### 검색어 삭제
자동완성 대상에 폭력적이거나 혐오성이 짙은 등 위험한 결과를 필터링해야 한다.
API 서버와 트라이 캐시 사이에 필터 계층을 두어 응답을 필터링할 수 있다.
(실제 데이터를 물리적으로 삭제하는 로직은 별도로 비동기적으로 수행하면 된다.)

## 저장소 규모 확장
트라이 데이터가 큰 경우, 샤딩을 통해 확장성을 지원해야 한다.
a~z 까지 알파벳 순으로 샤딩을 한다면?
특정 알파벳으로 시작하는 단어 수가 많은 경우 hot-key 문제가 발생할 수 있다. (c 로 시작하는 단어는 매우 많다)

![[Pasted image 20261006215010.png]]
따라서 위와 같이 데이터의 패턴에 따라 동적으로 데이터를 샤딩하는 구조를 사용할 수도 있다.

#### 검색어 대응 샤드 관리자 동작 예시
샤드 관리자는 **접두어 범위 → 샤드** 매핑 테이블을 들고, 데이터 양이 비슷해지도록 범위를 나눈다.
- ex) `s`로 시작하는 검색어 수 ≈ `u`~`z`로 시작하는 검색어 수를 합친 것이라면, 샤드를 아래처럼 나눈다.

| 접두어 범위 | 샤드 |
| ----------- | ---- |
| `a` ~ `r`   | 샤드 1 |
| `s`         | 샤드 2 |
| `t`         | 샤드 3 |
| `u` ~ `z`   | 샤드 4 |

1. 사용자가 `sun`을 입력하면, 웹 서버는 샤드 관리자에게 "`sun`은 어느 샤드에 있나?"를 묻는다. → **샤드 2**
2. 웹 서버는 샤드 2에서 `sun` key의 인기 검색어를 조회해 응답한다.
- 이후 `s` 데이터가 더 커지면, 관리자가 `sa`~`sm` / `sn`~`sz` 처럼 범위를 더 잘게 쪼개 새 샤드로 옮기고 매핑 테이블만 갱신한다.

## 4단계 - 마무리

- **다국어 지원** : 비영어권 언어도 지원하려면 트라이에 **유니코드** 데이터를 저장해야 한다.
- **국가별로 인기 검색어 순위가 다른 경우** : 국가별로 **다른 트라이**를 사용한다. 트라이를 **CDN**에 저장해 응답 속도를 높일 수도 있다.
- **실시간으로 변하는 검색어 추이(trending) 반영** : ex) 갑자기 큰 뉴스가 터져 특정 검색어가 급상승하는 경우
	- 현재 설계로는 어렵다.
		- 작업 서버가 주 1회만 트라이를 갱신한다.
		- 갱신하더라도 트라이를 새로 구성하는 데 시간이 너무 오래 걸린다.
	- 책에서 제시하는 아이디어
		- **샤딩**을 통해 작업 대상 데이터 양을 줄인다.
		- **순위 모델을 변경**해 최근 검색어에 더 높은 가중치를 준다.
		- 데이터가 스트림 형태로 계속 들어오므로 **스트림 처리 시스템**을 사용한다. (Hadoop MapReduce, Spark Streaming, Storm, Kafka 등)
	- 해결책 (개인 정리)
		- **배치 + 실시간 이중 구조** : 기존 주간 배치 트라이는 그대로 두고, 급상승 검색어만 처리하는 **실시간 계층**을 따로 둔다.
			- 질의 서비스는 `배치 트라이의 top-k` + `실시간 trending top-k`를 **합쳐서(merge)** 응답한다.
			- 무거운 트라이 재구성 없이 실시간성만 추가할 수 있다.
		- **슬라이딩 윈도우 집계** : Kafka로 검색 로그를 받아 Flink/Spark Streaming에서 최근 N분(ex. 10분) 윈도우 단위로 빈도를 센다.
			- 평소 대비 증가율이 큰 검색어만 trending으로 판단한다. (절대 빈도가 아니라 **증가율** 기준이어야 늘 많이 찾는 검색어와 구분된다)
		- **시간 감쇠(time decay) 점수** : `점수 = 빈도 × e^(-λ × 경과 시간)` 처럼 오래된 검색일수록 점수를 깎아 최근 검색어가 위로 올라오게 한다.
		- **근사 알고리즘으로 메모리 절약** : 모든 검색어를 정확히 셀 필요 없이 **Count-Min Sketch + top-k 힙**으로 상위 검색어만 근사 집계한다.
		- **결과 저장** : 접두어별 trending top-k를 Redis 같은 인메모리 저장소에 **TTL**과 함께 저장한다. 유행이 지나면 자연스럽게 만료된다.
