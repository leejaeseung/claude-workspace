검색어 자동완성 시스템

사용자가 글자를 입력할 때마다, 그 글자로 시작하는 가장 인기 있는 검색어 5개를 100ms 안에 보여주는 시스템을 설계한다.

TrieTop-k 캐싱Key-Value 저장소브라우저 캐싱샤딩
발표 팁 : ← → 키로 섹션 이동
🔍

    글자 하나를 칠 때마다 서버에 요청이 1번씩 간다. dinner 한 번 검색 = 요청 6번.

    STEP 01

    요구사항

    면접관과의 질의응답으로 도출한 다섯 가지 요구사항.

    ⚡

    빠른 응답 속도

    입력마다 충분히 빠르게. 페이스북은 100ms 이내.

    🎯

    연관성

    입력과 연관된 검색어. 여기선 접두어 매칭.

    📊

    정렬

    인기도 순위 모델로 정렬. 여기선 질의 빈도 순.

    📈

    규모 확장성

    많은 트래픽을 감당하도록 확장 가능.

    🛡️

    고가용성

    일부 장애가 나도 계속 동작.

    STEP 02

    개략적 규모 추정

    하루 천만 명이 쓰는 검색창이라면, 서버는 초당 몇 번의 요청을 받을까?

    10,000,000일간 사용자
    ×
    10인당 검색
    ×
    20검색당 요청 (20자)
    ÷
    86,400하루(초)
    ≈
    24,000 QPS

    평균 4단어 × 5글자 = 20바이트(ASCII). 최대 QPS는 2배인 48,000. 질의 중 20%가 신규라면 하루 0.4GB씩 데이터가 늘어난다.

    STEP 03

    개략적 설계 : 빈도 테이블

    가장 단순한 출발점. 검색어마다 횟수를 세고, 많이 검색된 순으로 5개를 꺼낸다.

    ① 데이터 수집 서비스

    검색이 들어올 때마다 frequency + 1

    queryfrequency

    ② 질의 서비스

    접두어 "tw" 입력 시

    SELECT * FROM frequency_table
WHERE query LIKE 'tw%'
ORDER BY frequency DESC
LIMIT 5
    문제

    데이터가 많아지면 LIKE 'tw%' + 정렬이 매 글자마다 실행된다. 초당 24,000번은 DB가 버틸 수 없다 → 트라이로 해결.

    STEP 04

    트라이(Trie) 자료구조

    retrieval에서 온 이름. 문자열의 공통 접두어를 공유하는 트리다. 노드 하나 = 글자 하나, 루트에서 노드까지의 경로 = 접두어. 검색어 노드에는 빈도를 함께 저장한다.

    ① 접두어 경로 ② 순회하는 서브트리 실제 검색어 노드(빈도)
    1. ① 접두어 노드 찾기 O(p)
    2. ② 서브트리 전체 순회 O(c)
    3. ③ 빈도순 정렬 O(c log c)

    최적화 두 가지로 O(1) 만들기

    1. 접두어 최대 길이 제한

    사람은 긴 검색어를 거의 입력하지 않는다. 길이를 50 같은 상수로 막으면 O(p) → O(1).

    2. 노드마다 인기 검색어 캐시

    각 노드에 top-k를 미리 저장. ②③ 단계가 사라진다. 위 데모에서 "노드별 top-k 캐시"를 켜 보자.

    대가 : 저장 공간 증가. 응답 속도가 중요한 자동완성에선 감수할 만한 트레이드오프.

    STEP 05

    데이터 수집 서비스

    검색할 때마다 트라이를 고치면 질의 서비스가 느려진다. 인기 검색어는 자주 바뀌지 않으니, 로그를 모아 주기적으로 트라이를 만든다.

    분석 로그검색 질의를 append만
    (수정 없음)
    →
    로그 취합 서버실시간성 요구에 맞춰
    취합 주기 조절
    →
    취합된 데이터query · frequency
    (주 단위 집계)
    →
    작업 서버주기적으로
    트라이 재구성
    →
    트라이 DB영속 저장소
    →
    트라이 캐시DB 스냅샷을
    분산 캐시에

    트라이를 Key-Value 저장소(해시 테이블)에 저장하기

    노드 하나 → 항목 하나. key = 접두어, value = 그 노드의 top-k. 트리를 탐색할 필요 없이 get("be") 한 번이면 끝.

    keyvalue
    영단어 전부를 넣으면?

    약 17만 단어 → 노드 약 50만 개 × 항목당 약 80B ≈ 40MB (어림 계산). 노드 수만큼 항목이 생긴다.

    빈도가 바뀌면? : 쓰기 증폭

    0 번 쓰기

    검색어 하나의 빈도가 바뀌면 그 검색어의 모든 접두어 key(beer, bee, be, b)를 읽고 → 순위 재계산 → 덮어써야 한다. 위 표에서 노랗게 바뀌는 행을 보자.

    쓰기 증폭

    갱신 1회 = 검색어 길이 p만큼 쓰기. 약 O(p × k log k).

    Hot key 경합

    b, be 같은 짧은 key는 수많은 검색어가 공유 → 갱신이 몰린다.

    캐시 정합성

    트라이 캐시에도 같은 변경을 반영해야 한다.

    그래서 책의 선택

    질의마다 갱신하지 않고, 작업 서버가 주기적으로 트라이를 새로 만들어 통째로 교체한다.

    페이지 그대로 유지

    브라우저 캐싱

    결과는 잘 안 바뀌니 브라우저에 저장. 같은 접두어는 서버에 안 간다.

    1회차 "be" → 서버 요청
    2회차 "be" → 브라우저 캐시
    Cache-Control: private, max-age=3600

    구글 : 사용자 브라우저에만, 1시간

    데이터 샘플링

    모든 질의를 로깅하면 CPU·저장 공간 낭비. N개 중 1개만 기록.

    N = 10 : 요청 50개 중 5개만 로그로 남는다

    STEP 07

    트라이 연산

    생성

    작업 서버가 취합된 로그·DB 데이터로 트라이를 만든다.

    갱신

    ① 새 트라이로 통째 교체 권장

    ② 노드 개별 갱신 느림
    모든 상위 노드까지 갱신 필요 (STEP 05의 쓰기 증폭)

    삭제

    혐오·폭력적 검색어는 필터 계층에서 걸러낸다. 물리 삭제는 나중에 비동기로.

    API 서버

    필터 계층위험 검색어 제거
    →
    트라이 캐시
    ⇢
    트라이 DB물리 삭제는 비동기
    STEP 08

    저장소 규모 확장 : 샤딩

    트라이가 커지면 나눠 담아야 한다. 첫 글자 a~z로 26개 샤드에 나누면?

    첫 글자별 영단어 비율 (대략적인 분포, 예시)

    Hot shard

    s, c로 시작하는 단어는 x, z의 수십 배. 알파벳 단위로 자르면 일부 샤드에만 데이터와 트래픽이 몰린다.

    검색어 대응 샤드 관리자

    데이터 양이 비슷해지도록 접두어 범위 → 샤드 매핑을 관리한다. 웹 서버는 ① 관리자에게 샤드를 묻고 ② 그 샤드에서 데이터를 꺼낸다.

    접두어 범위샤드
    1. ① 어느 샤드에 있나?
    2. ② 샤드에서 데이터 추출

    s 하나 ≈ u~z 전체. s가 더 커지면 sa~sm / sn~sz로 쪼개고 매핑 테이블만 바꾼다. 웹 서버 로직은 그대로.

    STEP 09

    마무리 : 면접관의 추가 질문

    Q1 다국어 지원은?

    트라이에 유니코드 데이터를 저장한다.

    Q2 국가별 인기 검색어가 다르면?

    국가별로 다른 트라이. CDN에 올려 응답 속도 향상.

    Q3 실시간 급상승 검색어는?

    현 설계로는 어렵다. 주 1회 갱신 + 트라이 재구성이 느리다.

    Q3 해결책 : 배치 + 실시간 이중 구조

    무거운 트라이 재구성은 그대로 두고, 급상승 검색어만 처리하는 가벼운 실시간 계층을 옆에 붙인다.

    배치
    (주 1회)
    검색 로그
    →
    작업 서버주간 집계
    →
    트라이안정적인 top-k
    실시간
    (분 단위)
    Kafka검색 로그 스트림
    →
    Flink / Spark10분 슬라이딩 윈도우
    증가율 + 시간 감쇠
    →
    Redis접두어별 trending top-k
    TTL로 자동 만료
    ↓ 두 결과를 merge ↓
    질의 서비스배치 top-k + trending top-k → 최종 5개
    증가율 기준

    절대 빈도가 아니라 평소 대비 증가율로 판단해야, 원래 늘 많이 찾는 검색어와 구분된다.

    시간 감쇠 점수

    빈도 × e^(-λ·Δt) : 오래된 검색일수록 점수를 깎는다.

    근사 집계

    Count-Min Sketch + top-k 힙으로 상위 검색어만 근사 집계해 메모리 절약.
