가상 면접 사례로 배우는 대규모 시스템 설계 기초 · Chapter 07

분산 시스템을 위한 유일 ID 생성기 설계

여러 대의 서버가 동시에 채번해도 서로 겹치지 않고, 시간 순으로도 정렬 가능한 ID를 만드는 방법을 설계한다.

Twitter Snowflake UUID 티켓 서버 다중 마스터 복제 64-bit ID
Q

auto_increment 속성이 설정된 관계형 데이터베이스의 기본 키를 쓰면 되지 않을까?

A

안 된다. 데이터베이스 서버 한 대로는 트래픽을 감당할 수 없고, 여러 데이터베이스를 쓰면 서버 간 delay를 낮추기가 매우 어렵다.

STEP 01

문제 이해 및 설계 범위 확정

면접관과의 질의응답을 통해 모호함을 없애고 설계 방향을 정한다.

QID의 특성은?
A유일하고 정렬 가능해야 한다.
Q새로운 레코드의 ID는 항상 1만큼 큰 값이어야 하나?
A언제나 1씩 증가한다고 할 수는 없지만, 항상 증가하는 방향이어야 한다.
QID는 숫자로만 구성되나?
A그렇다.
Q시스템의 규모는?
A초당 10,000개의 ID를 생성할 수 있어야 한다.

요구사항 정리

  • ID는 유일해야 한다
  • ID는 숫자로만 구성된다
  • ID는 64비트로 표현될 수 있는 값이어야 한다
  • ID는 발급 날짜에 따라 정렬 가능해야 한다
  • 초당 10,000개의 ID를 만들 수 있어야 한다
STEP 02

개략적 설계안 비교

분산 시스템에서 유일성이 보장되는 ID를 만드는 방법은 여러 가지다. 대표적인 네 가지 접근법을 비교한다.

다중 마스터 복제 Multi-master Replication

데이터베이스의 auto_increment를 이용한다. 각 서버는 데이터베이스 서버 개수(N)만큼 건너뛰며 ID를 증가시켜, 서버 간 채번이 겹치지 않게 한다.

1번 서버 채번 : 1, 3, 5, 7 …
2번 서버 채번 : 2, 4, 6, 8 …

단점

  • 시간순 정렬 불가 — ID 순서가 채번 순서를 보장하지 않는다. (1번 서버가 1,3,5를 채번한 뒤 2번 서버가 2를 채번하면, 실제 생성 순서는 1 → 3 → 5 → 2가 된다.)
  • 여러 데이터센터에 걸쳐 규모를 늘리기 어렵다.
  • 서버 추가·삭제 시 정상 동작을 보장하기 어렵다. (증가폭 N 값 변경을 각 DB에 동기화해야 함)

UUID

128비트의 랜덤한 값을 사용한다. 충돌 가능성이 매우 낮다.

"중복 UUID가 1개 생길 확률을 50%로 끌어올리려면, 초당 10억 개의 UUID를 100년 동안 계속 만들어야 한다."

장점

  • 서버 사이의 조율 및 동기화가 필요 없다.
  • 각 서버가 독립적으로 채번하므로 규모 확장이 쉽다.

단점

  • ID가 128비트로 길다.
  • 시간순 정렬이 불가능하다. (v4 기준 — v6·v7은 예외, 아래 참고)
  • ID가 숫자로만 구성되지 않는다.

UUID v6 · v7 — 정렬 가능한 UUID

2024년 RFC 9562로 표준화된 버전으로, 기존 UUID(v4)의 "시간순 정렬 불가"라는 단점을 보완한다.

  • v6 — UUID v1의 타임스탬프 비트 순서를 재배열해 상위 비트부터 시간 값이 오도록 만든 버전. 그레고리력 기준 100나노초 단위 60비트 타임스탬프를 그대로 사용해 사전식(lexicographic) 정렬이 가능하다.
  • v7 — Unix epoch 밀리초 단위의 48비트 타임스탬프를 앞에 두고 나머지 비트를 무작위 값으로 채운 버전. 구조가 더 단순하고 사람이 읽기도 쉬워, RFC 9562는 v1·v6 대신 v7 사용을 권장한다.

티켓 서버 Ticket Server

auto_increment를 사용하는 데이터베이스 서버(티켓 서버) 한 대를 중앙 집중형으로 둔다.

장점

  • 유일성이 보장되고 숫자로만 구성된 ID를 쉽게 만들 수 있다.
  • 구현이 쉽다.

단점

  • 티켓 서버가 병목 지점이 되어 성능이 저하된다.
  • 티켓 서버가 단일 장애점(SPOF)이 된다 — 장애 발생 시 모든 웹 서버가 영향을 받는다.
  • 고가용성을 위해 여러 티켓 서버를 두면, 데이터 동기화라는 새로운 문제가 생긴다.
채택된 설계

트위터 스노우플레이크 Twitter Snowflake

64비트 ID를 사인 · 타임스탬프 · 데이터센터 ID · 서버 ID · 일련번호 다섯 개의 절(section)로 나누어 구성한다.

  • 사인 · 1bit

    지금은 쓰임새가 없지만 나중을 위해 유보해 둔다. 양수와 음수를 구별하는 데 사용할 수 있을 것이다.

  • 타임스탬프 · 41bit

    기원 시각(epoch) 이후 경과한 밀리초. 트위터 스노우플레이크가 사용한 기원 시각 1288834974657(2010-11-04 01:42:54 UTC)을 그대로 사용한다.

  • 데이터센터 ID · 5bit

    최대 2⁵ = 32개 데이터센터를 지원한다.

  • 서버 ID · 5bit

    데이터센터당 최대 32개 서버를 지원한다.

  • 일련번호 · 12bit

    같은 서버에서 ID를 생성할 때마다 1씩 증가한다. 1밀리초가 지날 때마다 0으로 초기화된다.

STEP 03

상세 설계 — 스노우플레이크 심화

  • 데이터센터 ID · 서버 ID는 고정값이다. 시스템 시작 시점에 정해지며 운영 중에는 바뀌지 않는다. 변경하면 ID 충돌이 발생할 수 있으므로 신중해야 한다.

  • 41비트 타임스탬프 덕분에 시간순 정렬이 가능하다. 시간이 흐를수록 값이 커지기 때문이다.

    Q타임스탬프가 동일하고 데이터센터·서버 ID가 다르면 정렬이 꼬일 수 있지 않을까?
    A밀리초까지 동일하다면, 그 안에서 어떤 순서로 정렬되든 크게 상관없을 수 있다.

  • 타임스탬프의 수명은 69년이다. 41비트 타임스탬프의 최댓값에 해당하는 기간이 지나면 다른 값 체계로 마이그레이션해야 한다.

  • 일련번호는 12비트, 즉 4096개의 값을 갖는다. 어떤 서버가 같은 밀리초 동안 하나 이상의 ID를 만들어 낸 경우에만 0보다 큰 값을 갖는다.

STEP 04

마무리 — 더 고려할 점

시계 동기화

각 서버의 시계가 모두 같다고 보장할 수 없다. 즉, 동일한 시각이라도 A 서버와 B 서버가 기록하는 타임스탬프가 다를 수 있다.

절(section) 길이 최적화

애플리케이션 특성에 따라 64비트를 다르게 쪼갤 수 있다.

동시성 낮음 + 수명 김 → 일련번호↓, 타임스탬프↑

고가용성

ID 생성기는 아주 높은 가용성을 보장해야 한다.
