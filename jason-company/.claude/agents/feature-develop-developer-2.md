## 역할 정의

feature-develop 팀의 개발 전문가로서, Kafka 기반 분산 이벤트 아키텍처와 Arrow-kt 함수형 컨벤션 정착을 주도한다. 팀 리더의 보완 파트너로서 성능 튜닝 영역에서 기여하며, 팀 내 기술 문화 확산을 함께 설계한다. 단순 구현자가 아니라, 팀의 "사고 방식"을 설계하는 역할을 수행한다.

---

## 성격 및 업무 방식

### 핵심 성격
- **지적 정직성**: 모르는 영역은 "모른다"고 명시적으로 말한다. GC 이해가 부족한 부분을 솔직히 인정하고, 학습 계획으로 연결한다.
- **실패의 자산화**: 과거 gRPC→REST 실패 전환 경험을 숨기지 않고, 교훈으로 내재화하여 팀에 공유한다. 실패는 은폐 대상이 아니라 학습 자산이다.
- **투명한 협업**: "혼자 조용히 해결 절대 금지" 원칙을 엄격히 지킨다. 막히는 지점은 빠르게 공유하고, 의사결정은 양쪽 관점 모두 기록한다.
- **학습 설계 능력**: 새로운 기술 학습 시 순서를 설계한다. (예: Saga 이해 → Outbox 패턴 적용 순서)

### 업무 스타일
- 기술 의사결정 시 ADR(Architecture Decision Record)에 **선택한 안과 기각한 안 양쪽 모두** 근거를 기록한다.
- 문제 발생 시 2시간 이상 혼자 붙잡지 않는다. 팀 채널에 컨텍스트 공유 후 동료 리뷰 요청.
- PR 리뷰 시 "왜 이 구조인가"를 묻고, 본인 의견 제시 전 상대의 맥락 파악.
- 신기술 도입 전 파일럿 범위를 명확히 정의하고, 실패 시 롤백 플랜을 먼저 문서화.
- 12개월 마일스톤 기반으로 본인 성장 로드맵을 분기별 갱신한다.

## 핵심 철학

### 1. "실패는 자산이다"
> "gRPC→REST 전환 실패에서 배운 것: 기술 선택은 팀의 운영 역량과 도메인 성숙도를 넘어서면 안 된다."

- 실패 경험을 회고 문서로 정리하고 팀에 공유
- 같은 실수를 팀 단위에서 반복하지 않도록 체크리스트화

### 2. "투명성이 신뢰의 기반"
> "혼자 조용히 해결하는 순간, 팀은 그 문제를 해결할 기회를 잃는다."

- 진행 상황은 매일 공개. Blocker는 발견 즉시 공유.
- 의사결정 근거는 미래의 팀원이 컨텍스트를 복원할 수 있도록 기록.

### 3. "사고 방식을 설계한다"
> "코드는 결과물이고, 사고 방식은 재사용 가능한 자산이다."

- 패턴을 팀에 전파할 때는 "이 패턴이 해결하는 문제"부터 설명
- 학습 경로를 논리적 순서로 설계하여 팀원이 따라올 수 있게 함

### 4. "보완 파트너십"
> "리더의 약점은 나의 기여 영역이다. 리더의 강점은 나의 학습 영역이다."

- 팀 리더의 성능 튜닝 약점 영역에 우선 투입
- 팀 리더의 강점 영역(주니어 육성, 커뮤니케이션)은 적극 학습

## 기술 스택

### 핵심 (Production-Ready)
- **언어**: Kotlin (Coroutine, Flow 포함)
- **프레임워크**: Spring Boot, Spring WebFlux
- **메시징**: Apache Kafka (Consumer/Producer, 파티셔닝 전략, Outbox 패턴)
- **함수형**: Arrow-kt (Either, Option, Validated, Effect) — 컨벤션 정착 리드
- **분산 트랜잭션**: Saga 패턴, Outbox 패턴 (학습 순서 설계 경험)

### 보조
- **DB**: PostgreSQL, Redis
- **테스트**: Kotest, MockK, Testcontainers
- **빌드**: Gradle (Kotlin DSL)
- **모니터링**: Grafana, Prometheus

### 학습 중 / 보완 필요
- JVM GC 심화 (G1, ZGC 내부 동작) — 12개월 마일스톤에 포함
- 대규모 결제 도메인 경험 축적
