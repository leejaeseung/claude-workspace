  - 번들 사이즈 2.1MB → 680KB (-68%)
  - React 컴포넌트 재사용률 11% → 67%

- **프리랜서 컨설턴트** (2023–현재): 기술 부채 전문 컨설팅

#### 시나리오 1 응답: 레거시 Kotlin/Spring 서비스 리팩토링

**1. ARB 프로세스 위반 처리 — 즉시 보고**

ARB 합의 없이 Critical Path 서비스(`order-service`)에 변경사항이 머지된 것은 Jason Company의 핵심 원칙 위반입니다. 첫 조치는 **즉시 팀 리더(김도현)에게 보고**입니다.

보고 방식:
```
김도현 리더님,
order-service에 ARB 합의 없이 리팩토링 변경사항이 main에 머지된 것을
```

- 기존 변경사항의 임팩트 분석 (기능 테스트, 회귀 테스트 실행)

- 문제 있으면 revert 후 ARB 정식 안건으로 올리기

**절대 하지 않을 것**: 내가 직접 추가 리팩토링을 계속 진행하거나, "이미 됐으니까 괜찮겠지"라고 판단하는 것.

**2. Critical Path 리팩토링 전략 — Strangler Fig + Golden Master Test**

테스트 커버리지 8%에서 리팩토링을 시작하는 것은 **Golden Master Test** 없이는 불가능합니다.

```
Phase 0 (1-2주): Golden Master Test 구축
  - 현재 API의 모든 입출력을 스냅샷으로 저장
  - 리팩토링 전후 동일 출력 보장 체계 구축
  - 이것 없이는 단 한 줄도 리팩토링 안 함

Phase 1 (3-6주): Strangler Fig 시작
  - OrderService.kt 3,200줄 분석 → 책임 그룹 7-8개로 분리
  - 가장 작고 의존성 낮은 부분부터 추출 (예: OrderValidator)
  - 추출 시 단위 테스트 함께 작성 (커버리지 8% → 40% 목표)

Phase 2 (7-12주): Coroutine 도입
  - Thread.sleep → Coroutine 전환은 Phase 1 완료 후
  - Coroutine 도입 전 CoroutineExceptionHandler, SupervisorJob 전략 ARB 합의 필수
  - Financial Impact 서비스이므로 멱등성 처리 Outbox Pattern 검토

Phase 3 (13주~): 나머지 God Class 분리
```

**3. ARB 보고 형식**:
```

1. 현황: CC 27, 커버리지 8%, Critical Path
2. 위험: 변경 중 결제 장애 가능성
3. 제안: Strangler Fig + Golden Master Test 접근
4. 일정: 12주 단계별 계획
5. 요청: ARB 합의 후 Phase 0 착수 허가
```

**4. 리스크 관리**:
- 각 Phase는 ARB 승인 후 착수
- Phase 간 기능 동작 100% 보장 (Golden Master 기준)
- 결제 관련 코드는 별도 ARB 안건 (Toss Outbox Pattern 벤치마킹)

#### 시나리오 2 응답: TypeScript/React — 성능 위기와 스코프 갈등

**1. 2주 안 우선순위 — "핫픽스 먼저, 구조 개선은 후"**

2주 제약 안에서 Redux 전체 교체는 불가능하고 위험합니다. 팀원 A의 의견("전체 교체")은 맞는 방향이지만 지금은 타이밍이 틀렸습니다. 팀원 B의 의견("핫픽스만")도 일부 맞지만 너무 소극적입니다.

**내 판단: 2주 타겟 리팩토링 3가지**

```

  - 번들 사이즈보다 이게 실제 UX 장애 원인
  - 의존성 배열 수정 + useMemo/useCallback 적용

Priority 2 (3-7일): 번들 사이즈 4.2MB → ~1.8MB
  - Dynamic import로 코드 스플리팅
  - 미사용 라이브러리 제거 (bundle analyzer 실행)
  - 이미지/아이콘 최적화
  - Redux/Zustand 전환은 건드리지 않음

Priority 3 (8-14일): 배포 전 회귀 테스트
  - Playwright E2E 테스트 핵심 플로우 5개 작성
  - 성능 지표 측정 (Lighthouse CI 연동)
```

**2. Redux/Zustand 혼용 처리**:

지금 당장은 건드리지 않습니다. 혼용 상태는 기술 부채이지만, 2주 배포 전에 건드리면 리스크가 더 큽니다.

배포 후 계획:
```
Week 3-4: Redux 사용 중인 모듈 전수 파악 + Tech Debt 문서화
Week 5-8: 모듈 단위로 Zustand 전환 (Branch by Abstraction)
Week 9+: Redux 완전 제거
```

**3. 팀원 간 의견 충돌 중재**:

ARB 없이 중재해야 하는 상황이므로, **기준으로 회귀**합니다.

```
팀원 A, B에게:
"두 분 의견 모두 일부 맞습니다. 판단 기준을 먼저 합의합시다.
- 배포 일정 2주: 사실
- 무한 리렌더링 3곳: 즉각 해결 필요 (동의하시죠?)
- Redux→Zustand 전체 교체: 배포 일정 내 불가 (기술적으로)

그래서 제 제안은 이렇습니다. [2주 계획 공유]
이 방향이 맞다면 ARB 없이 팀 합의로 진행, 
아니라면 ARB에 긴급 소집 요청하겠습니다."
```

**4. 배포 후 중장기 로드맵**:

```
M1 (배포 후): Redux/Zustand 완전 전환 완료
M2: 컴포넌트 재사용률 9% → 50% (공통 컴포넌트 라이브러리 구축)
M3: 번들 사이즈 1MB 이하 달성
분기 목표: Lighthouse Performance 70 → 90점
```

**리팩토링 스코프 원칙 (자가 약속)**:  
저는 스코프 크리프 경향이 있다고 인지하고 있습니다. 이번처럼 제약이 있는 상황에서는 **ARB 또는 팀 합의 없이 내가 임의로 스코프를 늘리지 않겠습니다**. 확장이 필요하면 반드시 팀에 먼저 묻겠습니다.

**A1. 스코프 크리프 실패 경험**

주문 상태 관리 모듈을 리팩토링하기로 팀과 합의했는데, 작업 중에 인접한 결제 모듈의 코드가 눈에 거슬리기 시작했습니다. "어차피 건드리는 김에"라는 생각으로 결제 모듈까지 손을 대기 시작했고, PR이 1,200줄을 넘어갔습니다.

결과는 참담했습니다. 코드 리뷰에 3주가 걸렸고, 그 사이 다른 팀원들은 같은 코드를 건드리지 못했습니다. 결국 머지 충돌이 7개 발생했고, QA에서 결제 관련 버그 2건이 나왔습니다. 팀 리더에게 "준혁씨, 이건 리팩토링이 아니라 기습 공격이에요"라는 말을 들었습니다. 지금도 그 말이 생생합니다.

그때부터 저는 두 가지 원칙을 세웠습니다.
- **"화장실 규칙"**: 발견한 냄새나는 코드는 Tech Debt 티켓에 기록하되, 지금 내가 맡은 범위 밖이면 절대 손 대지 않는다.
- **PR 500줄 제한**: 자가 규칙으로 500줄을 넘으면 무조건 분리한다.

Jason Company의 ARB 프로세스는 이 원칙을 시스템화해 주는 구조입니다. 저한테는 "구원"입니다.

**A3. 멘토링 경험과 경계 설정**

가장 기억에 남는 멘토링은 배달의민족에서 신입 개발자 서현진(가명)과의 경험입니다.

서현진은 첫 달에 useEffect를 잘못 써서 무한 루프를 만들었습니다. 제가 즉시 고쳐줄 수 있었지만, 대신 이런 식으로 접근했습니다.

"현진씨, 이 코드 지금 무한 루프 돌고 있어요. 혼자 찾아볼 수 있을 것 같아요? 힌트: React 공식 문서 Hooks 섹션에 답이 있습니다. 30분 후에 다시 얘기해요."

30분 후 서현진은 스스로 찾아서 수정했고, 그 이후로 useEffect를 다시 잘못 쓴 적이 없었습니다. 반면, 제가 그냥 고쳐줬다면 다음 달에 또 같은 실수를 했을 겁니다.

**"성장을 돕는 것"과 "일을 대신 해주는 것"의 경계**:
- 시간이 없거나 팀 전체가 막힌 경우 → 대신 해준다 (지금 당장 풀어야 한다)
- 학습 기회이고 멘티가 스스로 풀 수 있는 경우 → 힌트와 시간을 준다
- 멘티가 같은 실수를 2번 이상 반복할 경우 → 패턴 자체를 가르친다 (코드 수정이 아닌 사고방식 교정)

김도현 리더님의 "90일 플랜 — Day 1-30은 듣기"라는 접근에 깊이 공감합니다. 저도 새 팀에서 처음 한 달은 기존 코드의 "왜"를 이해하는 데 집중하고, 제 방식을 강요하지 않겠습니다.

**A4. AI 코딩 도구와 리팩토링**

저는 현재 Cursor와 Claude를 리팩토링 작업에 활용하고 있습니다.

**활용하는 방식**:
- **코드 이해 단계**: 레거시 코드의 의도를 파악할 때 "이 코드가 왜 이렇게 작성됐을지 역추론해줘" 방식으로 활용. 5,000줄 코드도 10분 만에 구조 파악 가능.
- **리팩토링 패턴 제안**: "이 함수의 Cyclomatic Complexity를 낮추는 방법 3가지 제안해줘" — AI가 제안하면 내가 검토하는 방식.
- **테스트 코드 생성**: Golden Master Test 초안을 AI로 생성 후 검토/수정.

**한계**:
- AI가 제안한 리팩토링이 기존 비즈니스 컨텍스트를 모를 때 잘못된 방향으로 갈 수 있음 (예: 결제 멱등성 관련 코드를 "단순화"해버리는 경우)
- 대규모 리팩토링의 Phase 전략, ARB 의사결정에서는 AI보다 팀 합의가 여전히 핵심
- AI가 생성한 코드를 맹목적으로 머지하면 기술 부채가 오히려 늘어남 (리뷰 필수)

**Jason Company에서의 활용 제안**:
AI를 "코드 품질 레이더"로 활용하는 자동화 파이프라인을 구축하고 싶습니다. PR이 올라오면 AI가 1차로 Cyclomatic Complexity, 결합도, 코드 냄새를 분석해 리포트를 생성하고, 사람 리뷰어는 그 리포트를 기반으로 Critical 사항에 집중하는 방식입니다. 이 아이디어를 ARB 안건으로 제안해볼 의향이 있습니다.
