#### 시나리오 1: 기능 설계 — OOP vs FP 판단과 확장성

**상황**:  
당신은 Jason Company feature-develop 팀의 첫 태스크를 받았습니다.

**요구사항**: 사용자 포인트 적립 시스템
```
- 사용자가 구매 완료 시 포인트를 적립한다
- 포인트 계산 규칙:
  - 일반 회원: 구매금액의 1%
  - VIP 회원: 구매금액의 3%
  - 특별 이벤트 기간: 모든 회원 2배 적립
- 포인트는 적립 후 만료되지 않는다 (현재 요구사항)
- 향후 추가 예정: 포인트 만료 정책, 등급별 추가 규칙, 파트너사 포인트 연동
```

당신에게 주어진 시간은 이틀입니다. 지금 당장 동작하는 코드를 만들어야 하지만, "향후 추가 예정" 항목을 고려한 설계가 필요합니다.

#### 시나리오 1 응답: 포인트 적립 시스템 설계

**OOP vs FP 판단**:

이 요구사항은 **OOP + FP 혼합**으로 설계합니다.

- **OOP 쓰는 이유**: 회원 등급, 이벤트 정책은 상태와 행위가 묶인 도메인 개념 → 객체로 표현이 자연스러움
- **FP 쓰는 이유**: 포인트 계산 자체는 순수 함수(입력 → 출력, 부수 효과 없음) → 함수 합성으로 표현하면 테스트·확장이 쉬움

**핵심 설계 원칙**:
```
계산 규칙 = 순수 함수 (FP)
도메인 개념 (회원, 이벤트) = 객체 (OOP)
조합 방식 = 전략 패턴 + 함수 합성
```

**Kotlin 설계 스케치**:

```kotlin
// 1. 포인트 계산 규칙을 순수 함수 타입으로 정의 (FP)
typealias PointCalculator = (purchaseAmount: Long) -> Long

// 2. 기본 계산 규칙 (순수 함수)
val normalMemberRate: PointCalculator = { amount -> amount / 100 }       // 1%
val vipMemberRate: PointCalculator = { amount -> amount * 3 / 100 }      // 3%
val doubleEventBonus: (PointCalculator) -> PointCalculator =
    { base -> { amount -> base(amount) * 2 } }                           // 2배

// 3. 회원 등급을 sealed class로 표현 (OOP)
sealed class MemberGrade {
    object Normal : MemberGrade()
    object VIP : MemberGrade()
}

// 4. 계산기 선택 (OOP로 상태 관리, FP로 계산)
fun resolveCalculator(grade: MemberGrade, isEventPeriod: Boolean): PointCalculator {
    val base: PointCalculator = when (grade) {
        MemberGrade.Normal -> normalMemberRate
        MemberGrade.VIP    -> vipMemberRate
    }
    return if (isEventPeriod) doubleEventBonus(base) else base
}

// 5. 포인트 적립 서비스
class PointService(private val pointRepository: PointRepository) {
    fun accrue(userId: Long, purchaseAmount: Long, grade: MemberGrade, isEventPeriod: Boolean) {
        val calculator = resolveCalculator(grade, isEventPeriod)
        val points = calculator(purchaseAmount)
        pointRepository.save(userId, points)
    }
}
```

**"지금 동작" vs "미래 확장" 균형**:

향후 추가 예정 항목들을 이 설계가 어떻게 수용하는지:
- **포인트 만료 정책**: `PointRepository.save(userId, points, expiresAt?)` — 현재 `null`로 넘기고, 만료 정책 추가 시 `expiresAt` 파라미터만 채움. **기존 코드 수정 없음.**
- **등급별 추가 규칙**: `MemberGrade`에 새 케이스 추가 + `resolveCalculator`에 `when` 분기 추가. 다른 곳 영향 없음.
- **파트너사 포인트 연동**: `PointCalculator` 타입은 그대로, 파트너사별 다른 함수를 주입. `PointService` 수정 없음.

**이틀 안에 완성 우선순위**:
```
Day 1 오전: 핵심 계산 로직 + 단위 테스트 (순수 함수라 테스트가 쉬움)
Day 1 오후: PointService + PointRepository 인터페이스 설계
Day 2 오전: PointRepository 구현체 + 통합 테스트
Day 2 오후: 리뷰 + 배포 준비

이틀 안에 완성 불가한 것:
- 파트너사 포인트 연동 (요구사항 명세 불명확) → Tech Debt 티켓
- 이벤트 기간 자동 감지 (별도 이벤트 서비스 의존) → 수동 파라미터로 대체, 이후 개선
```

#### 시나리오 2 응답: NotificationService 채널 추가

**결론부터**: **오늘 배포에는 `when` 블록에 추가합니다. 리팩토링은 하지 않습니다.**

**판단 근거**:

| 기준 | 오늘 배포 | 리팩토링 후 배포 |
|------|---------|--------------|
| 배포 시간 | ✅ 오늘 가능 | ❌ 2-3일 추가 |
| 리스크 | ✅ 낮음 (3줄 추가) | ⚠️ 중간 (전체 구조 변경) |
| OCP 준수 | ❌ 위반 | ✅ 준수 |
| 기술 부채 | ⬆️ 증가 | ⬇️ 해소 |

기능 추가 자체가 목적이고, 오늘 배포가 비즈니스 요구사항일 때는 **최소 변경으로 배포하는 것이 옳습니다**. 단, 이것이 기술 부채임을 팀에 명시적으로 알려야 합니다.

**오늘 구현**:
```kotlin
fun notify(userId: Long, message: String, channel: String) {
    when (channel) {
        "EMAIL"       -> emailSender.send(userId, message)
        "SMS"         -> smsSender.send(userId, message)
        "KAKAO_TALK"  -> kakaoTalkSender.send(userId, message)  // 추가
        else          -> throw IllegalArgumentException("Unknown channel: $channel")
    }
}
```

**트레이드오프 설명 (리팩토링하지 않은 선택)**:
- 리팩토링했다면 `NotificationHandler` 인터페이스 + 각 채널별 구현체 + `Map<String, NotificationHandler>` 조회 구조로 OCP 준수 가능
- 장점: 이후 채널 추가 시 `when` 수정 불필요
- 단점: 지금 당장 불필요한 복잡도 추가 + 배포 지연
- **지금은 채널이 3개** — "Rule of Three"가 아직 충족 안 됨. 한 개 더 추가되면 리팩토링 시점

**배포 후 Tech Debt 처리**:
```
배포 직후:
1. Tech Debt 티켓 생성:
   "NotificationService when 블록 OCP 리팩토링 필요.
   채널 3개 → 4개 이상 시 즉시 진행.
   리팩토링 방향: NotificationHandler 인터페이스 + Map 기반 조회."

2. PR에 주석:
   // TODO: 채널 4개 이상 시 NotificationHandler 인터페이스로 리팩토링 필요 (#TICKET-XXX)
```

**핵심 원칙**: "기술 부채를 만드는 것"과 "기술 부채를 숨기는 것"은 다릅니다. 오늘 부채를 만들되, 팀 전체가 볼 수 있는 곳에 명시합니다.

**A1. OOP·FP에서 바뀐 생각**

처음 OOP를 배울 때는 "상속이 코드 재사용의 핵심"이라고 믿었습니다. 우아한형제들 초기에 배달 경로 계산기 클래스를 만들면서 `BaseCalculator`를 상속받는 `FastCalculator`, `EcoCalculator`, `CustomCalculator`를 만들었습니다. 처음에는 깔끔해 보였는데, 3개월 후 새 요구사항이 생기면서 계층 구조가 엉켜버렸습니다. `FastEcoCalculator`가 필요해졌을 때, 어떤 클래스를 상속받아야 하는지 명확하지 않았고, 결국 기존 클래스를 많이 뜯어고쳐야 했습니다.

그때 시니어 분이 "Composition over Inheritance를 한번 생각해봐"라고 했고, 그 코드를 전략 패턴으로 다시 짰습니다. 새 요구사항이 와도 기존 코드를 건드리지 않고 새 전략만 추가하면 됐습니다.

그 이후 FP를 공부하면서 "함수 합성이 상속보다 더 유연한 재사용 방법"이라는 것을 체험했습니다. 지금은 재사용이 필요할 때 "상속"을 먼저 떠올리지 않습니다. "이 행위를 어떻게 합성할 수 있을까?"를 먼저 묻습니다.

바뀐 생각 한 문장으로: **"재사용은 상속으로 하는 것이 아니라 합성과 주입으로 한다."**

---

**A2. 1년, 3년 비전**

**1년 후 — "독립적으로 기능 하나를 처음부터 끝까지 책임질 수 있는 개발자"**:
지금 저는 기능 구현 자체는 자신 있지만, 요구사항의 모호한 부분을 스스로 정의하는 것은 아직 부족합니다. 1년 후에는 "이 기능, 어디까지 만들어야 해요?"라고 팀 리더에게 묻는 것이 아니라, 제가 먼저 "이렇게 해석했는데 맞나요?"라고 말할 수 있게 되고 싶습니다.

**3년 후 — "지금은 못 하는 두 가지를 할 수 있는 개발자"**:
- 첫 번째: **시스템 간 통신 설계** — 서비스 내 기능 설계는 자신 있지만, 이벤트 기반 비동기 통신, 서비스 간 의존성 관리는 아직 시니어 도움이 필요합니다. 3년 후에는 이 설계를 스스로 할 수 있고 싶습니다.
- 두 번째: **다른 사람의 설계를 읽고 개선안을 제안하는 능력** — 지금은 제 코드의 문제는 잘 보이는데, 다른 사람 코드의 구조적 문제를 파악하고 팀에 납득 가능한 개선안을 제안하는 것은 아직 자신이 없습니다.

이 두 가지를 위해 지금 의도적으로 하는 것이 있습니다: 팀 코드 리뷰에서 "왜 이렇게 설계됐을까?"를 먼저 추론하고, 그 다음 내가 다르게 했을 것 같은 부분을 노트에 정리합니다. 틀려도 상관없다고 생각합니다. 추론 습관을 만드는 것이 목적입니다.

---

**A3. 확장성이 오히려 부담이 된 실패 경험**

당근 재직 시절입니다. 매칭 점수 계산 시스템을 설계할 때, "앞으로 여러 요소가 추가될 것"이라는 생각에 `ScoringFactor` 인터페이스 + `CompositeScoringFactor` + 팩토리 패턴까지 설계했습니다. 초기 요구사항은 사실 "거리 점수 + 카테고리 점수" 두 가지뿐이었습니다.

결과는 두 가지 문제가 생겼습니다.

첫째, 신입 팀원이 "이 코드를 이해하는 데 3시간 걸렸다"고 했습니다. 두 가지 요소를 계산하는 코드가 5개 파일에 나뉘어 있었기 때문입니다.

둘째, 실제로 추가된 요소는 7개월 후 딱 1개였고, 그 1개는 제가 예상한 방향과 달랐습니다. 제 설계가 그 방향을 수용하기 위해 오히려 일부를 수정해야 했습니다.

거기서 배운 것: **확장성 설계는 "모든 방향"을 미리 열어두는 것이 아닙니다. "가장 발생 가능성 높은 한두 가지 방향"만 열어두는 것이 좋은 설계입니다.** 나머지는 실제로 요구사항이 생겼을 때 그때 대응해도 늦지 않습니다. 저는 그때 "미래를 너무 많이 열어두려다가 현재를 복잡하게 만들었습니다."

지금 시나리오 1에서 `typealias PointCalculator`로 설계한 것도 같은 이유입니다. "모든 방향"이 아닌 "계산 규칙 교체"라는 가장 발생 가능성 높은 방향 하나만 열어두었습니다.

---

**A4. OOP·FP 학습에서 가장 어려웠던 순간**

FP를 처음 배울 때 `Monad`를 이해하려고 했을 때입니다. 블로그와 책을 읽을수록 더 헷갈렸습니다. "Monad is just a monoid in the category of endofunctors"라는 설명을 읽고 한동안 FP 공부를 포기했습니다.

극복 방법: 이론을 버리고 코드부터 시작했습니다. Kotlin의 `Result.map`, `Result.flatMap`을 먼저 실제 코드에서 반복해서 써보고, "이게 뭔지 모르겠지만 이렇게 쓰면 null 안전하게 체이닝이 된다"는 것을 몸으로 익혔습니다. 그 다음에 Arrow-kt의 `Either`를 써보면서 "이게 Monad처럼 작동하는구나"를 체험으로 이해했습니다.

지금 코드에 미친 영향: 저는 새로운 개념을 배울 때 이론보다 코드 예제를 먼저 씁니다. "이 개념으로 실제로 해결할 수 있는 문제가 뭔가?"를 먼저 찾습니다. OOP·FP를 조합하는 방식도 마찬가지입니다. "OOP가 더 자연스러운 문제"와 "FP가 더 자연스러운 문제"를 체험으로 구분하게 되었습니다. 이론적으로 정답을 먼저 정하지 않습니다.
