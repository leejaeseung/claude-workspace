#### 시나리오 1: 패턴이 보이는 상황에서의 절제 — 단순 코드 vs. 패턴 도입

**상황**:  
Jason Company의 알림 발송 모듈(`notification-service`)을 코드 리뷰하던 중 다음 코드를 발견했습니다.

```kotlin
fun sendNotification(type: String, userId: Long, message: String) {
    when (type) {
        "EMAIL" -> emailClient.send(userId, message)
        "SMS"   -> smsClient.send(userId, message)
        "PUSH"  -> pushClient.send(userId, message)
    }
}
```

당신의 눈에는 즉시 **Strategy 패턴**과 **Factory 패턴**을 조합할 기회가 보입니다. 알림 타입이 현재 3개이고, 앞으로 2-3개 더 추가될 예정입니다. 이 코드는 Critical Path는 아니고, 팀원 2명이 이 모듈을 주로 담당합니다.

단, 현재 이 변경은 **ARB 안건으로 등록되어 있지 않습니다**. 당신은 이 코드 리뷰에서 패턴 적용을 제안할 권한이 있습니다.

**평가 포인트**:
1. 이 코드에 지금 당장 Strategy+Factory 패턴을 적용해야 하는가? 기준은 무엇인가?
2. ARB 안건 없이 코드 리뷰 단계에서 패턴 적용을 어떻게 처리할 것인가?
3. 팀원 2명이 이 모듈을 담당하는 상황에서 패턴 도입을 어떻게 제안할 것인가?
4. "단순함을 유지할 때"와 "패턴을 도입할 때"의 기준선을 명확히 제시하라.

#### 시나리오 2: Anti-pattern 발견 — 즉각 수정 vs. ARB 경유

**상황**:  
Jason Company의 주문 도메인 코드(`order-domain`)를 분석하다가 심각한 Anti-pattern을 발견했습니다.

```kotlin
// OrderService.kt (1,800줄)
class OrderService(
    private val userRepo: UserRepository,
    private val productRepo: ProductRepository,
    private val paymentService: PaymentService,
    private val inventoryService: InventoryService,
    private val notificationService: NotificationService,
    private val auditService: AuditService,
    private val reportingService: ReportingService  // 7개 의존성
) {
    fun createOrder(request: OrderRequest): Order {
        // 결제, 재고, 알림, 감사 로그, 리포팅이 한 메서드 안에서 처리됨
        // 비즈니스 로직, 인프라 로직, 도메인 로직이 모두 뒤섞임
    }
}
```

이 코드는 God Class + Anemic Domain Model + Feature Envy가 동시에 발생한 전형적인 Anti-pattern입니다. 당신이 보기에 Facade 패턴으로 의존성을 정리하고, Domain Event + Observer 패턴으로 알림/감사/리포팅을 분리하면 즉시 개선 가능합니다.

그런데 이 서비스는 **월 결제 처리량 45만 건의 Critical Path**이고, **ARB 안건으로 등록되지 않은 상태**입니다. 팀 리더 김도현은 현재 다른 긴급 장애 대응 중이라 바로 연락하기 어려운 상황입니다.

**평가 포인트**:
1. Anti-pattern이 명확히 보이는 상황에서 ARB 없이 어떻게 행동할 것인가?
2. Critical Path 서비스에 패턴 리팩토링을 제안하는 방법과 절차는?
3. 팀 리더가 바로 연락 안 되는 상황에서의 에스컬레이션 방식은?
4. "Anti-pattern 발견 → 개선 제안 → ARB 합의 → 실행"의 구체적 프로세스는?

### [후보 — 박지수] 시나리오 응답

---

#### 시나리오 1 응답: 패턴 적용 절제 판단

**결론부터**: 지금 당장 Strategy+Factory 패턴을 적용하지 않습니다.

**판단 근거 — 제 "패턴 도입 3기준"**:

```
패턴 도입이 정당화되려면 다음 중 2개 이상을 충족해야 합니다:
1. 현재 코드가 변경에 닫혀 있는가? (Open/Closed Principle 위반이 실제로 발생하고 있는가?)
2. 동일한 구조적 문제가 3곳 이상 반복되는가? (Rule of Three)
3. 팀원이 이 코드를 이해하는 데 어려움을 겪고 있는가?
```

이 코드에 적용하면:
- 기준 1: when 블록이 2-3개 더 추가될 **예정**이지만, **지금은 아직 아님**. 확장이 발생했을 때 도입해도 늦지 않음.
- 기준 2: 단일 when 블록으로 현재 코드 자체는 읽기 쉬움. 팀원 2명이 이 모듈을 이해하는 데 어려움이 없음.
- 기준 3: 팀원이 어려움을 겪고 있다는 증거 없음.

**결론: 3기준 중 0개 충족. 패턴 도입 보류.**

**코드 리뷰에서의 처리 방식**:

```
코드 리뷰 코멘트 (Question 분류):
"이 when 블록, 앞으로 타입이 몇 개 더 추가될 예정인가요?
3개 이상 추가되면 Strategy 패턴 도입을 ARB 안건으로 올릴 가치가 있을 것 같습니다.
지금 당장은 현재 코드가 충분히 읽기 쉽다고 생각해요."
```

**ARB 없이 처리 가능한 범위**:
- 코드 리뷰에서 "미래 패턴 도입 가능성"을 기록하는 Tech Debt 티켓 생성
- ARB 안건은 **실제로 확장 필요가 발생했을 때** 올림
- 지금 당장 패턴을 적용하는 것은 YAGNI(You Aren't Gonna Need It) 원칙 위반

**팀원 2명에게의 제안 방식**:
```
1:1로 이준혁, 김도현 팀원에게:
"notification-service의 when 블록, 타입 추가 예정 맞죠?
3개 이상 되면 Strategy 패턴으로 전환하는 게 유지보수에 좋을 것 같아요.
타이밍 봐서 같이 ARB 안건으로 올려볼까요?"
```

**"단순함 유지" vs "패턴 도입" 기준선**:
- **단순함 유지**: 코드가 이미 의도를 명확히 드러내고, 변경 빈도가 낮으며, 팀원 모두가 이해 가능한 경우
- **패턴 도입**: 동일 구조가 3회 이상 반복되거나, 실제 확장 요구가 발생하거나, 변경이 두렵다는 피드백이 나올 때
- **핵심 원칙**: "패턴은 문제 해결 도구이지, 코드를 '아름답게' 만드는 도구가 아닙니다."

저는 과거에 이 기준 없이 "좋아 보이는" 패턴을 도입했다가 팀에 부담을 준 경험이 있습니다. 지금은 이 3기준을 엄격히 지킵니다.

#### 시나리오 2 응답: Critical Path Anti-pattern — ARB 없이의 행동 원칙

**결론부터**: 코드를 한 줄도 건드리지 않습니다. 대신 즉시 문서화하고 에스컬레이션합니다.

**즉각 행동 (같은 날)**:

**Step 1: Anti-pattern 분석 문서 작성**
```markdown
[긴급 Tech Debt 문서] order-domain Anti-pattern 분석
발견일: 오늘
발견자: 박지수

발견된 Anti-pattern 3가지:
1. God Class: OrderService 1,800줄, 의존성 7개
2. Anemic Domain Model: 비즈니스 로직이 서비스 레이어에 모두 집중
3. Feature Envy: 알림/감사/리포팅이 OrderService 책임 범위 초과

예상 영향: 결제 처리 45만 건/월 — 변경 시 고위험
제안 패턴:
- Facade: 7개 의존성 정리
- Domain Event + Observer: 알림/감사/리포팅 분리

ARB 안건 등록 요청 (긴급)
```

**Step 2: 팀 리더(김도현)에게 비동기 에스컬레이션**
```
슬랙 메시지 (긴급 장애 방해 최소화):
"[비긴급, 장애 해결 후 확인 부탁] 
order-domain에서 God Class + Anemic Domain Model 발견.
Critical Path(결제 45만건/월)라 즉각 수정 않고 문서화만 해뒀습니다.
ARB 안건으로 올리기 전 리더님 검토 필요합니다. 
[문서 링크] — 해결 완료 후 15분 내 확인 부탁드립니다."
```

**Step 3: 절대 하지 않을 것**
```
❌ 김도현 리더가 바로 연락 안 된다고 해서 내가 판단하여 수정 착수
❌ "어차피 Anti-pattern이니까 고쳐도 되겠지"라는 자의적 판단
❌ 다른 팀원에게 ARB 우회 승인 요청
```

**이유**: Critical Path 서비스에 대한 아키텍처 변경은 ARB 만장일치가 필요한 사항입니다. 아무리 명확한 Anti-pattern이라도 ARB 합의 없이 변경하면, 그게 오히려 새로운 기술 부채가 됩니다. 제 판단이 옳더라도 프로세스를 지키는 것이 팀 신뢰의 기반입니다.

**ARB 안건 제출 형식**:
```
[ARB 안건] order-domain Anti-pattern 개선 — Facade + Domain Event 적용
1. 현황: God Class(1,800줄), 의존성 7개, Anemic Domain Model
2. 위험도: Critical Path (결제 45만건/월) — 고위험
3. 제안: 
   - Phase 1: Facade 패턴으로 의존성 정리 (저위험)
   - Phase 2: Domain Event + Observer로 알림/감사 분리 (중위험)
   - Phase 3: Anemic Domain Model 개선 (고위험, 별도 ARB)
4. 각 Phase ARB 별도 승인 요청
5. Phase 1 착수 전 테스트 커버리지 최소 60% 확보 조건
```

**저의 원칙**: "Anti-pattern을 발견했을 때 가장 위험한 행동은 즉각 고치는 것입니다. 두 번째로 위험한 행동은 아무것도 하지 않는 것입니다. 옳은 행동은 기록하고, 알리고, 합의를 구하는 것입니다."

**A1. Over-engineering 실패 경험**

가장 부끄럽게 기억하는 건 Line Corp 재직 시절 2018년입니다.

사내 로그인 모듈을 리뷰하다가 인증 방식이 단순한 if-else 체인으로 구현된 것을 보았습니다. 저는 즉시 "Abstract Factory + Strategy 패턴을 조합하면 훨씬 확장성 있겠다"고 판단하고, 팀 리더 허락도 없이 PR을 작성해 제출했습니다. 코드 자체는 기술적으로 올바른 패턴이었습니다.

결과는 다음과 같았습니다. 코드 리뷰에 2주 반이 걸렸고, 팀원 3명이 "이걸 이해하려면 Factory 패턴부터 다시 공부해야 한다"는 피드백을 남겼습니다. 리뷰어 중 한 명은 "지수씨, 이 코드가 맞긴 한데, 우리가 이걸 유지보수할 수 있을까요?"라고 했습니다. 결국 PR은 더 단순한 방식으로 재작성되어 머지되었습니다.

그 사건 이후 제가 바뀐 것 두 가지:
- **변경 전 팀원 이해도 확인**: "이 패턴, 팀원 중 몇 명이 이해할 수 있을까?"를 항상 먼저 묻습니다. 팀 전체가 이해 못하는 패턴은 아무리 좋아도 기술 부채입니다.
- **패턴 제안 전 승인 요청**: 지금은 패턴 적용 PR을 올리기 전에 반드시 담당 팀원과 먼저 이야기합니다. 코드를 쓰기 전에 사람을 먼저 설득합니다.

Jason Company의 ARB 프로세스는 이 두 번째 원칙을 제도화한 것이어서 저한테는 자연스럽게 느껴집니다.

**A3. 팀원 교육 철학 — 패턴 지식 전달**

Line에서 180명을 교육하면서 가장 크게 배운 것은 **패턴을 가르치는 것이 아니라 패턴이 필요한 상황을 느끼게 해야 한다**는 것입니다.

저의 교육 접근법:

**"먼저 문제, 나중에 패턴"**:
```
나쁜 방법: "오늘은 Observer 패턴을 배우겠습니다. Observer 패턴이란..."
좋은 방법: "이 코드에서 구독자가 100개가 되면 어떻게 될까요? 직접 고쳐보세요.
            5분 후에 다들 비슷한 구조를 만들었을 거예요. 그게 Observer 패턴입니다."
```

**"이미 아는 사람"과 "처음 배우는 사람" 동시 대상 접근**:
- 처음 배우는 사람: 코드를 직접 짜보게 하여 패턴의 필요성을 체험
- 이미 아는 사람(이준혁, 김도현 리더님): "이 패턴, 우리 팀 코드베이스 어디에 적용 가능할까요?" — 실무 적용 토론으로 전환

Jason Company에서는 월 1회 "실전 패턴 리뷰 세션"을 제안하고 싶습니다. 실제 코드 PR을 가져와서 "이 코드에 패턴을 적용해야 할까, 말아야 할까?"를 함께 토론하는 방식입니다. 이 세션의 결론이 쌓이면 자연스럽게 팀의 "패턴 의사결정 가이드"가 됩니다.

**A4. Coroutine 약점 보완 계획**

솔직하게 말씀드리면, 저의 Coroutine 경험은 "알고 있다"와 "실무에 자신 있다"의 중간 어딘가입니다. 이론은 이해하고 있으나 Production 레벨의 실전 경험이 부족합니다.

**학습 계획**:
- 입사 첫 3개월: Kotlin Coroutines Deep Dive (Roman Elizarov 저) 완독 + 팀 코드베이스에서 Coroutine 사용 패턴 전수 분석
- 3-6개월: 이준혁 전문가와 페어 프로그래밍으로 실제 Coroutine 코드 작성 경험 축적
- 6개월 이후: Coroutine 컨텍스트에서의 디자인 패턴 적용 (예: Coroutine 기반 State Machine 구현)

**팀 내 협력 구조**:
저와 이준혁 전문가의 협력은 자연스럽게 상호 보완적이라고 생각합니다.
- 이준혁: "이 코드를 Coroutine으로 어떻게 리팩토링할까?" → 저: "리팩토링 후 어떤 패턴 구조로 정착시킬까?"
- 저: "이 패턴, Coroutine 환경에서 안전하게 구현하려면?" → 이준혁: Coroutine 안전성 검토

약점을 숨기는 것보다 팀에서 서로의 강점으로 채우는 것이 더 건강하다고 생각합니다. 그래서 입사 첫날부터 이준혁 전문가에게 "Coroutine 멘토링 부탁드립니다"라고 먼저 말할 계획입니다.
