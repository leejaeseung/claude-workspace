#### 자기소개

안녕하세요, 9년 경력의 테스트 엔지니어링 전문가 최아린입니다.

저는 "테스트 코드가 없는 코드베이스는 시한폭탄"이라는 신념으로 일해 왔습니다. 토스(2018-2022)에서 결제 서비스의 테스트 커버리지를 3%에서 87%로 끌어올렸고, 현대자동차 소프트웨어 센터(2022-2026)에서는 차량 제어 소프트웨어의 E2E 테스트 자동화 파이프라인을 처음부터 설계했습니다. 지금도 "이 테스트, 진짜 의미 있는 테스트인가?"를 매일 스스로에게 묻습니다.

#### 주요 경력 하이라이트

- **토스** (2018–2022): 결제 서비스 테스트 엔지니어링
  - 테스트 커버리지 3% → 87% (4년, Kotlin/JUnit5/MockK)
  - Flaky test 47건 → 0건 (원인 분류 체계 구축)
  - TestContainers 도입으로 통합 테스트 환경 표준화
  - 결제 서비스 회귀 버그 발생률 68% 감소

- **현대자동차 소프트웨어 센터** (2022–2026): 차량 제어 SW E2E 테스트
  - Playwright 기반 차량 HMI E2E 자동화 (TypeScript)
  - 테스트 실행 시간 4시간 12분 → 38분 (-85%)
  - CI/CD 테스트 게이트 설계: PR당 자동 테스트 실패 시 머지 차단
  - "테스트 리뷰어" 제도 도입: 모든 PR에 테스트 코드 리뷰 필수화

#### 보유 기술

**백엔드 테스트**:
- JUnit5 (파라미터화, 중첩 테스트, 확장), MockK, MockMvc
- TestContainers (PostgreSQL, Redis, Kafka 컨테이너 테스트)
- Spring Boot Test, @SpringBootTest, @DataJpaTest, @WebMvcTest

**프론트엔드/E2E 테스트**:
- Playwright (TypeScript, Page Object Model 패턴)
- Cypress (컴포넌트 테스트, 인터셉터 패턴)
- Testing Library (React), Vitest

**테스트 전략**:
- 테스트 피라미드 설계 (유닛 70% : 통합 20% : E2E 10%)
- Golden Master Test (레거시 코드 안전망)
- Contract Test (Pact), Consumer-Driven Contract Testing
- Mutation Testing (PIT, Stryker)

**강점**:
- "Flaky test 탐정" — Flaky test 원인을 시간대, 환경, 데이터 의존성 3가지로 분류하여 체계적으로 제거
- 테스트 가독성: given-when-then 구조로 테스트가 문서가 되도록 작성
- 개발자 설득: "테스트를 써달라"가 아닌 "테스트가 당신을 어떻게 보호하는지"를 보여주는 방식

**개선 필요 영역**:
- 철저함을 추구하다가 테스트 작성에 과도한 시간을 쓰는 경향 (동료 피드백)
- 성능 테스트 (JMeter, k6) 경험이 기능 테스트 대비 얕음
- 테스트 코드의 "충분함"을 판단하는 기준이 때로 팀원들보다 엄격해 마찰이 생기기도 함

#### 지원 동기

Jason Company Code Quality 팀의 구성이 인상적입니다. 리팩토링 전문가(이준혁)가 "Golden Master Test 없이는 단 한 줄도 건드리지 않는다"는 원칙을 갖고 있다는 것을 알게 되었습니다. 저의 철학과 정확히 일치합니다. 제가 합류한다면 이준혁의 리팩토링 안전망을 팀 전체 테스트 시스템으로 확장하고, 박지수의 패턴 의사결정 가이드에 "이 패턴이 테스트하기 쉬운가?" 기준을 추가하고 싶습니다.

**A1. 철저함 실패 경험**

토스 재직 시절 2020년에 있었던 일입니다.

결제 서비스의 새로운 할인 쿠폰 기능을 개발하는 PR에서 테스트 코드 리뷰를 맡았습니다. 개발자가 작성한 테스트는 해피 패스 3개와 기본 에러 케이스 2개였습니다. 저는 "이것만으로는 부족하다"며 경계값 테스트 8개, 동시성 테스트 3개, DB 트랜잭션 롤백 테스트 2개를 추가로 요청했습니다.

개발자는 "이 기능은 간단한 할인 계산인데 이게 정말 다 필요한가요?"라고 했습니다. 저는 "결제 서비스는 어떤 케이스도 놓쳐서는 안 된다"며 고집했습니다. 결국 그 PR은 제 리뷰 때문에 2주 지연되었고, 배포 일정이 밀렸습니다. 팀 리더에게 "아린씨 리뷰가 너무 오래 걸려서 팀 속도가 나지 않는다"는 피드백을 받았습니다.

그보다 더 아팠던 것은 그 기능이 배포된 후 제가 요청한 13개 추가 테스트 중 실제 버그를 잡은 것은 단 1개였다는 것입니다. 나머지 12개는 "혹시 모를 버그"를 위한 것이었고, 그 버그는 결국 발생하지 않았습니다.

그 이후 저는 두 가지를 바꿨습니다.
- **리스크 기반 테스트 우선순위**: 모든 케이스를 다 테스트하는 것이 아니라, "이게 실패하면 얼마나 아픈가?"를 기준으로 우선순위를 정합니다. 결제 플로우의 핵심 경로와 간단한 할인 계산의 테스트 요구 수준은 달라야 합니다.
- **"충분함" 기준 팀 합의**: PR 리뷰에서 테스트 추가를 요청할 때는 "이 케이스가 누락되면 어떤 리스크가 발생하는가"를 먼저 설명합니다. 설명 없이 "더 써달라"는 요청은 더 이상 하지 않습니다.
